# System / Module / Component 设计模式

本模式从逻辑职责视角把软件划分为 System、Module、Component 三层：

```text
需求 / 领域
→ System：完整领域能力及公开契约
→ Module：System 私有的内聚子能力与信息隐藏边界
→ Component：有窄契约、可测试、可替换的单一职责代码单位
```

SMC 不要求所有协作都事件化。需要立即结果、拒绝原因或原子成功时优先使用显式
调用、命令或查询；只有当一个已经发生的事实需要被零个或多个独立能力感知时才
使用事件。本文的 EventBus 是可选的、进程内同步、类型化事件分发 Component：
它解除发布者与具体订阅者之间的直接认识，但不消除双方对事件契约的依赖，也不
改变 System、Module、Component 的职责、依赖和所有权。

设计必须自上而下进行：

```text
确定 System 的领域责任和公开契约
→ 按变化原因划分 Modules
→ 从 Module 职责中拆出 Components
→ 选择语言机制、成熟库和物理实现
```

不得从既有目录、类型、第三方库或预设 Component 清单反向塑造上层角色。

架构角色、代码定义、运行实例和物理工程单元彼此独立。System、Module、
Component 不强制对应某个类、对象、文件、目录、库、target 或进程。

## 模式边界

SMC 只定义逻辑职责、契约依赖、实例所有权和定义复用，不单独定义部署拓扑、
故障隔离、安全边界、持久化模型、实时调度、性能预算、多租户或版本发布。这些
视图必须与 SMC 边界对齐，但需要由具体产品另行定义。

本文以语言无关的方式定义进程内同步 EventBus，不绑定类、模板、接口、异常机制、
内存模型、运行时或第三方框架。EventBus 不代表线程调度器、异步队列、持久化日志
或跨进程消息总线；这些内容见[[集成消息与事件投递设计]]。

组合根、契约定义、普通函数、基础算法、生成代码和外部资源不必强行归类为
System、Module 或 Component：

- 组合根是组装机制，只负责选择、创建、注入、启动和关闭，不拥有领域规则；
- 契约属于现有角色、产品级协议权威或外部标准，不是独立运行层；
- 没有独立契约和生命周期的普通实现保持为模式外实现细节；
- 外部资源由取得其领域控制权的 System 负责，或通过明确的外部契约使用。

SMC 的源码或契约直接依赖、实例所有权和强生命周期约束保持无环。异步事件的
因果关系另行记录，不得伪装成结构依赖；需要反馈回路、双向消息、插件回调、
Actor 通信、点对点协议或共识交互时，各方应共同依赖中立协议契约，并由显式
Workflow、路由、宿主或协调 System 管理终止条件、幂等和防循环。运行时数据可以
双向流动，但参与方不得互相取得私有实现和生命周期。

## System

System 是面向一组完整领域需求的软件边界。

System 必须：

- 对外提供公开领域契约；
- 使用进程内 EventBus 协作时，拥有跨 Module 的 SystemEvent 契约、路由规则和
  EventBus 实例；跨 System 事件另由公开通信契约定义；
- 定义适用于自身的状态、策略和生命周期语义；无状态 System 必须明确声明无
  状态以及调用有效期；
- 选择并组织自己的 Module 定义；存在运行实例时负责创建和拥有 Module 实例；
- 负责跨 Module 的领域级流程、边界数据转换、失败策略和回滚；
- 只通过其他 System 的公开契约进行跨领域协作；
- 不得取得其他 System 的 Module、Component 或私有实现。

System-to-System 协作必须分别记录四种关系：

- **源码与契约依赖图**：谁导入谁的公开契约或 schema；
- **实例所有权与生命周期图**：谁创建、借用、启动和关闭谁；
- **同步可用性图**：一次调用成功时必须同时在线的 Systems（“在线”指实例已启动且可服务，与部署拓扑或进程形态无关）；
- **异步因果图**：哪些事件可能触发哪些后续事件和状态变化。

源码或契约直接依赖、实例所有权、强借用和启动先后约束必须显式、单向且无环。
同步可用性图可以双向或成环，因为两个独立启动的对等 Systems 可能分别调用彼此；
这种环不自动成为所有权或启动顺序，但必须显式记录共同故障域、延迟放大、超时、
取消、隔舱或熔断策略，并禁止无界的嵌套同步回调。异步因果图可以包含经过批准的
反馈回路，但必须由 Workflow/Application System 或中立协议管理，并明确
correlation、幂等、最大迭代或业务终止条件。不能通过字符串主题、全局 EventBus、
服务定位器或运行时发现隐藏任何一种关系。

EventBus 不改变这些规则。发布方可以不知道具体订阅者，但双方都依赖事件契约；
谁拥有契约、谁创建 Bus、谁注册处理器、谁持有订阅句柄以及谁决定业务响应必须
可查。事件流向、契约依赖方向和 EventBus 实例所有权必须分别记录。

每条进程内订阅必须进入可审查的路由清单，至少记录事件契约及所有者、发布方、
订阅方、事实建立点、注册位置、Bus 作用域、执行上下文、延迟或阻塞预算、失败策略、
重入策略和生命周期所有者。同步订阅等同于一条运行时调用边，必须纳入依赖环、锁
顺序和最长调用链审查；不能只在测试代码或运行时注册表中隐含存在。

运行时发现和动态插件并非禁止，但必须通过版本化契约、能力清单或插件清单明确
依赖，并由宿主或注册 System 管理发现、兼容、隔离、失效和卸载。不得把发现
机制当成绕过依赖审查的手段。

System 之间可能修改状态的契约必须按实际风险明确：

- 原子边界和部分成功语义；
- 幂等、重复调用、重试和去重语义；
- 超时、取消、并发冲突和背压语义；
- 补偿、恢复和错误上报责任；
- 异步消息的顺序、重复、丢失、确认和投递保证；
- 结果、句柄和订阅在提供方关闭后的失效方式。

System A 调用 System B 不表示 A 拥有 B。默认由组合根创建并持有顶层 System
实例。只有当 A 的领域责任明确包含 B 的完整生命周期时，A 才可以拥有 B。

实例所有权、强借用和真实的启动先后约束合并后必须仍可拓扑排序，该合并结果称为
启动拓扑图，必须无环。同步可用性图只在确实构成启动前置条件的边才进入启动拓扑图；
普通运行期调用关系单独分析，不得仅因调用成功要求双方在线就推导启动顺序。异步
因果边也不参与启动拓扑。所有者必须比被借用能力
存活更久；不得出现“A 拥有 B，但 B 必须在 A 之后启动或持有 A 的强借用”这类联合
环。启动按联合约束的正序执行，关闭按逆序执行。

跨多个 Systems 的领域用例由明确的 Workflow/Application System 负责。它可以
编排其他 Systems 的公开契约和事务，但不得取得其私有实现，也不得成为其他
Systems 领域状态的事实所有者。组合根不得承担这类领域编排。

## Module

Module 是所属 System 私有的内聚实现与信息隐藏单位。

Module 必须：

- 隐藏一组可能独立变化的设计决策；
- 使用事件时，拥有 ModuleEvent；默认把 Component 的窄输出映射为 ModuleEvent，
  或采用 System 私有事件契约，不把私有 Component 事件直接泄漏给其他 Modules；
- 封装适用于自身的局部状态、策略和生命周期；无状态 Module 可以只有定义而
  没有独立运行实例；
- 选择并连接 Components，管理自己私有拥有的 Component 实例；
- 不暴露内部 Component 实例或具体实现；
- 不决定其他 Module 或 System 的领域流程；
- 不依赖其他 System 的 Module。

Module 应按变化原因和信息隐藏划分，不得只按执行步骤、目录或文件数量切分。

同一 System 内确有稳定子能力依赖时，Modules 可以通过窄契约协作，但必须满足：

- 依赖由 System 私有边界拥有并记录，或由需求方 Module 声明能力端口；
- 依赖只面向抽象契约，不取得提供方的具体类型、实例、工厂或生命周期；
- 依赖图显式、单向且无环；
- System 在组装期选择实现并注入；
- 组装完成后，Modules 可以通过已注入契约直接协作，不要求 System 转发每次
  局部调用。

跨 Module 契约只要可能修改状态，就必须像跨 System 契约一样明确原子边界、
幂等、并发冲突、部分成功和补偿责任。System 对跨 Module 领域事务负最终责任，
可以通过工作单元、候选状态、事务上下文、补偿协议或其他机制落实；不得在没有
失败语义的情况下让 Modules 直接串联可变操作。

若两个 Modules 总是一起变化、共享大量内部状态或需要高频双向协作，应合并或
重新划分，而不是扩大契约。

Module 实例始终是消费 System 的私有实现。Module 定义只有在契约自包含、隐藏
决策相同且不引用原 System 私有类型时才能复用；这表示它可以在多个 Systems
中分别承担同一种私有实现角色，并不使 Module 成为跨 System 公开边界。每个
消费 System 必须分别创建并拥有自己的 Module 实例；跨 System 不得共享或访问
Module 实例。

Module 可以只使用一个 Component，但必须增加独立的子领域语义、信息隐藏、
状态、策略、生命周期或错误转换。若 Module 与 Component 契约相同且只做转发，
该 Module 是空壳。

## Component

Component 是从 Module 职责中拆出的单一职责原子代码单位。“原子”指在当前
领域约束下不能再合理拆分，不等于一个类、文件或函数。纯函数、参数化定义或
静态生成的算法只要满足 Component 契约，也可以没有独立运行实例。

Component 必须：

- 只有一项可以独立陈述的职责；
- 具有明确而窄的输入、输出、错误、线程和所有权契约；
- 隐藏内部实现；
- 可以独立测试；
- 可以在不改变 Module 语义的情况下替换实现；
- 不取得 Module 或 System 的对象、具体实现或生命周期；
- 不取得其他 Component 的具体类型、实例、工厂或生命周期。

Component 可以把结果作为返回值交回调用方，也可以通过自己拥有的窄输出契约
报告事实。Module 负责把 ComponentOutput 映射为 ModuleEvent 或更上层事件。
普通业务 Component 不得自行查找全局 EventBus、字符串主题或订阅者；需要发布
时只注入最窄的类型化发布能力，需要订阅时由所属 Module 或 System 在组装期注册，
并管理订阅生命周期。跨 System 消息由边界 Adapter 处理，不使用本文的进程内 Bus。

只有明确标为“边界感知”的私有 Component 才能采用所属 Module 或 System 的私有
事件类型；这会限制其复用范围，必须在契约中声明，不能再把它视为边界无关的
可复用 Component。

Component 可以使用标准库、私有辅助代码和由窄边界适配的成熟库。第三方类型、
错误模型和生命周期语义不得意外泄漏到 Module 或 System 契约。

System 的公开契约可以有意采纳外部标准、协议类型或原生句柄，但必须把该依赖
列为公开契约的一部分，并明确版本、兼容、错误、线程和生命周期责任。经过这种
显式采纳的类型属于公开设计选择，不视为实现泄漏。

同一 Module 内的 Components 可以通过以下方式协作：

```text
Component A → A 所需的窄能力契约
Module → 选择 Component B 或其他实现并注入

或：

Component A → Component B 的稳定抽象契约
Module → 选择 B 的具体实现并注入
```

Component 契约依赖必须显式、单向且无环。依赖抽象契约不表示依赖具体实现，
也不允许依赖方创建、查找或销毁提供方实例。

没有独立契约、替换价值或独立变化原因的代码，应保持为普通函数、私有类型或
基础算法，不应命名为 Component。

### Component 可见性

Component 身份与架构可见性分别判定：

- **私有 Component**：只服务于一个 Module，或由同一 System 内明确批准的多个
  Modules 使用；可以使用所属边界的私有语义；
- **可复用 Component**：契约脱离原 System 后仍有完整、稳定且自包含的原子
  语义，可以被多个 Modules 分别消费。

Adapter、Backend 和 Driver 描述环境适配责任，不与 Component 身份互斥。

私有 Component 提升为可复用 Component 必须满足：

- 契约不引用原 System 的私有类型、生命周期权威或领域错误策略；
- 存在明确的第二消费场景，或已确认的独立维护与测试价值；
- 提取不会泄漏原 Module 的私有决策或制造无实际需求的通用配置；
- 兼容、版本和依赖成本低于保留私有实现的成本。

跨 System 不得访问其他 System 的私有 Component。跨 System 复用应复用自包含
定义，或使用拥有方 System 的公开契约。

## 契约与类型所有权

| 契约所有者 | 契约用途 |
|---|---|
| System | 对外领域能力和跨 System 可见类型 |
| System 私有边界 | 本 System 的共享领域类型和跨 Module 能力 |
| Module | 组织内部 Components 所需的子领域类型和能力 |
| Component | 完成原子职责所需的输入、输出和可选能力 |
| 产品级协议权威或外部标准 | 不天然归属某个 System 的中立值、消息和互操作协议 |

产品级协议权威是契约归属，不是第四个运行层。它可以定义稳定的值语义、不可变
消息、参与角色、交互状态转换、correlation、超时和兼容规则，但不得包含业务实现、
运行时可变领域状态、服务定位或生命周期控制。

事件契约遵守相同的类型所有权规则。Component 默认只产生自己拥有的窄输出；
Module 将其显式映射为协调多个 Components 的 ModuleEvent。跨 Modules 的事件由
System 私有边界拥有，本文称为 SystemEvent。跨 Systems 的消息不通过同一个
进程内 EventBus 传播，其公开契约和投递规则见[[集成消息与事件投递设计]]。
边界感知的私有 Component 可以例外采用上层私有事件契约，但不得把这种耦合带入
可复用定义。

同一 System 内跨 Module 使用的契约由 System 私有边界拥有，或者由需求方
Module 拥有并由 System 适配。不得让某个 Module 的私有实现类型成为其他
Modules 的共同依赖。

除 System 契约显式采纳的外部标准类型外，下层实现类型不得泄漏到上层契约：

```text
Component 实现结果
→ Module 拥有的子领域语义
→ System 拥有的公开领域语义
```

转换可以使用移动、包装、只读视图或拥有型值，不强制复制数据；但类型、错误、
生命周期和所有权语义必须由当前边界拥有。

多个 Modules 使用的领域值由所属 System 私有边界定义。跨 Systems 可见的值
通常由提供能力的 System 公开契约拥有；若值表达对等协议、行业标准或不属于
任何单一提供方的共同语义，则由产品级协议权威或外部标准拥有。不得为了消除
依赖箭头把普通业务类型搬进中立契约。

System 对领域状态的语义负责；Module 可以保存其负责的子领域状态；Component
只保存完成原子职责所需的局部状态。

## Event 与进程内 EventBus

### 定位与适用条件

本节定义语言无关的架构语义。具体实现可以使用类、函数、协议、trait、接口、
生成代码或运行时注册表，只要满足本节的契约、作用域、生命周期和执行规则。

Event 表示已经发生的不可变事实。发布者不指定某个接收者，零个或多个订阅者可以
独立观察它；EventBus 只负责把事件按类型同步分发给当前已注册的处理器。它不拥有
业务状态，不决定业务流程，也不提供异步、排队、持久化、重试、重放或跨进程通信。

“已经发生”以对应边界声明的事实建立点 `FactEstablished` 为准：从该点起，边界把
命题视为成立，后续局部失败或回滚不能再把它改写为“从未发生”。事实建立点可以是
事务提交、Event Store 成功追加、原子状态转换、权威外部确认或其他等价机制，不以
特定语言和存储为前提。普通 Event 只能在该点之后发布；建立前的候选信息应保持为
`PendingEventRecord` 或显式事务通知，并通过调用链、Pipeline 或工作单元协调，不能
泄漏到普通 EventBus 或产生不可回滚的外部副作用。投递配置见
[[集成消息与事件投递设计]]。

先按交互语义选择机制：

| 需求 | 首选机制 |
|---|---|
| 需要返回值、拒绝原因或立即确认 | 直接接口、Command 或 Query |
| 只有一个固定接收者 | 普通函数、回调或窄接口 |
| 已发生的事实可被零个或多个能力独立感知 | 进程内 EventBus |
| 多步骤操作依赖固定顺序、补偿或总体结果 | 显式 Workflow / Process Manager |
| 需要换线程、延迟执行或背压 | 独立 Executor / Queue 设计 |
| 需要跨进程、持久化或重放 | [[集成消息与事件投递设计]] |

Event 应使用过去式事实命名，例如 `OrderConfirmed`，而不是 `ConfirmOrder`。需要
处理结果的 Command/Query 不得伪装成 Event；如果正确性取决于某个订阅者存在、
处理器返回值或固定调用顺序，也不应使用 EventBus。

### EventBus 核心思想

| 可借鉴思想 | 语言无关的 SMC 规则 |
|---|---|
| 事件不必继承统一基类 | 使用边界拥有的类型化事实契约，不强制共同对象模型 |
| 按事件类型注册与分发 | 发布者和订阅者共同依赖事件契约，不依赖彼此实现 |
| 注册产生作用域句柄 | 订阅生命周期显式，并能由所有者确定性释放 |
| 发布时立即调用处理器 | 同步执行上下文、耗时和失败会直接影响发布调用 |
| 并发访问受到保护 | 并发安全必须声明，但不等于异步、并行或线程迁移 |
| 同时支持开放与封闭事件集合 | 按扩展性、验证时点和治理成本选择类型集合策略 |

这些思想可以映射为作用域资源管理、`dispose/close`、上下文管理器、显式
`unsubscribe`、结构化并发作用域或其他等价机制，但任何一种具体 API 都不得成为
通用架构前提。

### SMC 边界映射

| 范围 | 契约所有者 | 默认交互 | EventBus 实例所有者 |
|---|---|---|---|
| Component → Module | ComponentOutput | 优先返回值或窄回调 | 通常不需要 Bus |
| 同一 Module 内多个 Components | ModuleEvent | 优先返回值或窄回调；仅在需要广播已建立事实时经 Module 私有 EventBus | Module |
| 同一 System 内跨 Modules | SystemEvent | System 作用域 EventBus | System |
| 跨 Systems | 公开消息契约 | 外部通信端口与 Adapter | 不使用本文的 EventBus |

推荐路径是：

```text
ComponentOutput
→ Module 判断它是否形成值得广播的事实
→ 所属边界越过 FactEstablished
→ 映射为 ModuleEvent 或 SystemEvent
→ 所属 Module/System 的 EventBus 同步分发
→ 已注册处理器通过自己的窄契约执行业务响应
```

不是每个输出都要事件化。Component 有固定调用者时直接返回；事件只在 Module 内
有价值时停在 Module；只有多个 Modules 都需要理解同一稳定事实时，才由 System
重新定义并拥有 SystemEvent。不得直接把 Component 私有类型提升为共享事件。

EventBus 实现可以作为可复用 Component 定义，但每个 Module 或 System 创建自己
的实例。普通业务 Component 只接收所需事件类型的发布 callable 或窄发布端口，
不取得完整 Bus、订阅表、销毁权或任意类型发布能力。订阅关系由所属边界在组装期
建立；组合根可以执行注册动作，但业务路由仍由 Module/System 决定。

### 类型与事件契约

事件优先定义为边界拥有的类型、记录、值对象或 schema，表达一个完整、不可变、
已经发生的事实。它不要求继承公共 `Event` 基类，也不得为了总线方便把所有事件
退化成字符串名称和无约束通用字典。

`ModuleEvent` 与 `SystemEvent` 描述契约所有者和可见范围；`DomainEvent`、
`TechnicalEvent` 等描述消息语义。这两个分类维度正交：一个表达已建立领域事实的
SystemEvent 同时也是 DomainEvent，但并非每个 SystemEvent 都具有领域事实语义。
`IntegrationEvent` 是跨 System 的版本化公开投影，属于集成消息契约，见
[[集成消息与事件投递设计]]，不在本文的进程内 EventBus 中传播。

事件负载必须：

- 由对应 Module 或 System 边界拥有，并使用该边界的语义命名；
- 使用拥有型值、不可变快照，或可观察内容与存活期在整个同步分发期间保持稳定的
  只读表示；
- 不携带可变引用、回调、资源句柄、事务对象、服务对象或发布者私有错误类型；
- 不要求订阅者回查发布对象才能理解基本事实；
- 对字段含义、单位、有效范围和线程可见性有明确约定。

默认按事件契约的精确身份分发，不因继承、原型链、接口实现、结构兼容或字段相似
而隐式扩大订阅范围。需要把一个事件解释成另一个概念时，由边界显式映射并记录
路由。处理器只能在同步分发有效期内使用临时借用的事件表示；若要延后处理，必须
复制或取得拥有权，不能保存可能失效的引用或视图。只读不等于稳定：底层数据若能
被并发改写，就必须先取得不可变快照或用等价机制冻结本轮可观察内容。

事件集合策略按边界选择：

| 策略 | 适用场景 | 代价与约束 |
|---|---|---|
| 封闭事件集合 | 稳定的 Module/System 私有事件集合 | 可在构建期或启动期完整验证；新增类型必须更新集合声明 |
| 开放事件集合 | 插件或确需运行时扩展的局部边界 | 错误更晚暴露；必须有类型清单、注册验证和未知类型策略 |

默认优先封闭事件集合，但不要为了集中声明而把整个产品的事件合并到同一个 Bus。
每个作用域只列出自己拥有和允许传播的事件。开放集合也必须使用稳定的事件契约
身份，不允许退化成无治理的任意对象容器。

EventBus 的发布契约不承诺业务应答。它可以返回仅用于诊断分发健康度的技术报告，
但发布方不得据此判断事实是否成立或某项业务是否被接受。需要收集业务结果、传播
拒绝或确认成功时改用直接接口；不得通过事件负载中的可变字段、共享容器或隐式
回调模拟返回值。

去重责任在发布方：同一事实不应重复发布，EventBus 不提供去重；重复发布造成的
重复观察由发布边界按已声明的幂等语义负责。

### 生命周期与所有权

EventBus、订阅句柄和接收对象具有严格的存活关系：

```text
活动订阅绑定及其发布快照访问期 ⊆ EventBus 的有效服务期
处理器访问目标状态的期间 ⊆ 目标状态有效或由安全所有权覆盖的期间
```

这约束的是活动绑定和状态访问，不要求所有语言采用同一种对象形态。默认采用强目标
绑定时，接收者必须比绑定及在途回调存活更久；采用弱引用、代际句柄或等价安全间接层
时，每次调用必须先原子取得有效访问权，失效后只能跳过，不能接触已销毁状态。句柄
对象本身可以在 Bus 关闭后存在，但只能是已经失效且释放安全的空壳，不能继续代表
活动绑定。弱/间接目标失效导致的跳过必须符合已声明的路由失败与生命周期策略，并
触发可诊断的绑定清理，不能用永久静默跳过掩盖必要观察者已经消失。所有者必须显式
落实以下默认顺序：

```text
启动：创建 EventBus → 创建接收对象 → 注册并保存句柄 → 开放事件入口
关闭：停止新发布 → 等待正在执行的回调至约定期限
      ├─ 已排空 → 释放句柄 → 销毁接收对象 → 销毁 EventBus
      └─ 已超时 → 执行声明的超时策略，不得销毁仍可能被回调访问的对象
```

每个订阅必须有一个可指出的所有者：通常由接收者持有自己的作用域订阅句柄，或由
Module/System 持有一组作用域订阅。句柄离开作用域、被关闭或显式取消时必须解除
绑定；释放操作应幂等，并在接收者内部依赖失效前完成。不得只依赖进程退出时的
隐式清理。

注销必须区分“从注册表移除”和“已经静默”：前者只保证新的发布快照不再取得该
处理器，已经取得快照或正在执行的回调仍可能访问接收者。接收者销毁前必须满足
以下任一安全回收契约：注销等待该订阅的在途回调归零；注销返回可等待的完成栅栏，
由所有者在销毁前等待；每个在途回调持有足以覆盖执行期的安全所有权；或回调通过
原子有效性检查取得访问权，失效时不再访问目标。处理器在自身回调内注销时不得同步
等待自己，应先禁止新的调用，并把静默完成和销毁延后到当前回调返回之后。仅从订阅
表删除处理器不足以证明接收者可以销毁。

关闭契约必须声明 drain deadline、超时报告位置，以及超时后继续等待、请求协作取消、
隔离未结束执行或使宿主关闭失败中的哪一种策略。运行环境不能安全取消处理器时，
不得伪造“强制取消”并继续销毁接收者或 Bus；阻塞处理器必须能被诊断到具体路由。
发出协作取消请求不等于处理器已经退出；只有确认回调已返回或不再能访问接收者后，
才可以释放句柄并继续销毁。

禁止使用全局单例、静态可变 Bus 或跨 System 共享 Bus 实例，因为它们会隐藏契约
依赖、初始化顺序和销毁顺序。组合根可以创建 Bus 并注入窄能力，但不能把整个 Bus
作为服务定位器交给任意代码。

每个活动订阅绑定必须只有一个释放责任方。实现若支持所有权转移，应先释放目标已有
绑定再接管新绑定；不支持时必须拒绝复制或转移，不能产生两个相互竞争的释放者。
Bus 在排空后统一失效绑定时，原句柄必须原子变为空壳；空句柄和重复释放必须安全。
Bus 关闭后不允许继续发布或注册；关闭期间的注销行为必须有明确语义，违规操作应
通过状态错误、诊断或测试暴露，而不是静默忽略。

### 同步执行、并发与顺序

`publish(event)` 是同步语义：返回前，本轮匹配的处理器已经执行完毕。除非具体
契约另有声明，处理器沿用发布者的执行上下文；EventBus 不自动切换线程、任务、
Actor、事件循环或调度器。因此：

- 发布调用的延迟包含全部处理器耗时；处理器应短小、有界且避免阻塞；
- UI、渲染、实时或上下文亲和代码必须验证当前执行上下文是否允许该处理器运行；
- 需要换线程时，由订阅者把自有数据复制到显式 Executor/Queue，不能假装 Bus
  已经异步；
- 默认不得在持有订阅者可能再次取得的业务锁、资源锁或可变状态保护器时发布。
  应在保护区内记录事件并取得稳定快照，释放保护后再分发；确需锁内发布时必须在
  路由清单中声明全局锁顺序、允许调用边和超时策略，并验证不会反向进入发布边界。

处理器执行顺序默认不是契约。业务正确性必须与注册顺序和容器遍历顺序无关；要求
A 完成后才能执行 B 时，应使用显式调用链、Pipeline 或 Workflow，而不是给
EventBus 增加隐式优先级。

实现必须声明并发发布、注册、注销和关闭能否并行，以及它们发生竞争时采用何种
快照或可见性语义。“并发安全”只表示共享状态不会损坏，不保证处理器并行。实现
应避免在持有订阅注册表的排他保护期间执行用户处理器；若无法避免，必须测量长
处理器造成的串行阻塞和饥饿风险。

默认禁止处理器在分发期间修改本 Bus 的订阅表或递归发布。实现若要支持，必须明确
本轮处理器快照、增删何时生效、嵌套事件顺序、深度限制和失败语义；业务代码不能
依赖未声明的可重入行为。确需级联事件时使用以下任一明确方案：

- 由上层协调者在本轮分发返回后发布下一个事件；
- 把待发布事件写入当前调用栈拥有的 pending 列表，最外层统一排空；
- 改用经过专门设计和测试的可重入 Dispatcher，先取得稳定处理器快照，再执行
  用户处理器。

同步调用不自动形成事务。多个处理器修改状态时，原子边界、失败回滚和外部副作用
仍由 Module/System 明确负责；需要全体处理器原子成功时，优先改成显式事务协调，
而不是依赖 EventBus 扇出。

### 失败策略与实现要求

不同语言可能使用异常、错误值、Result、Promise 拒绝、panic、进程信号或其他失败
机制；架构只要求处理器失败不能处于未定义状态。每个 EventBus 采用点必须先划分
可恢复处理器失败与进程级致命失败，再为可恢复失败选择并测试一种明确策略：

| 策略 | 规则 |
|---|---|
| 隔离并继续（默认） | 每个处理器失败独立记录或送入错误端口，不阻止其他处理器 |
| 全部执行后汇总技术失败 | 所有处理器仍执行；分发结束后把诊断报告交给调用方或统一错误处理器 |
| 任一失败都要回滚 | 不使用普通 EventBus，改用显式返回错误的调用链或事务协调 |

错误处理本身必须有失败边界，不得递归触发同一错误，也不得把失败静默转换为成功。
Event 所表达的事实不会因某个观察者失败而撤销；技术报告不得充当业务应答。若发布
接口不返回技术报告，至少要有可测试的错误端口、日志、指标或宿主故障策略。
运行环境无法安全捕获或隔离的进程级致命失败不属于进程内 EventBus 的继续分发保证；
需要此类隔离时，应使用进程、任务或运行时提供的故障边界，并在路由清单中声明。

实现必须满足：

- 注册、注销、发布和关闭失败可诊断，不能静默忽略；
- 订阅释放幂等，所有权转移不会遗留旧绑定或产生重复释放；
- 并发修改采用明确的处理器快照与可见性语义；
- 用户处理器不在订阅注册表的排他保护区内执行，或明确记录并验证相应阻塞风险；
- Bus 必须定义尚未接受发布、正常服务、关闭过程和关闭完成时各操作的行为；简单
  实现可以合并阶段，不强制暴露固定数量或名称的状态；
- Adapter 不泄漏第三方事件类型、错误机制和生命周期对象到业务 Components。

若采用第三方库，应把它包在 Module/System 私有 Adapter 后，锁定兼容版本，并让
业务代码只依赖本项目定义的窄发布能力。语言或运行时改变时可以替换实现，而不改变
SMC 角色和事件语义。

### 验证要求

EventBus 的最小充分验证包括：

- FactEstablished 之前的 PendingEventRecord 不会进入普通 EventBus，建立失败或
  回滚时没有观察者收到伪事实；
- 无订阅者时发布安全返回；多个订阅者都被调用，但测试不依赖调用顺序；
- 负载在整个同步分发期间的可观察内容保持稳定；临时只读表示不会被处理器修改、
  越期保存或在返回后继续访问；
- 只匹配精确事件类型，不把派生类型隐式投递给基类处理器；
- 注销的线性化点能阻止后续发布快照取得处理器，重复释放和所有权转移不遗留绑定；
- 并发发布与注销覆盖在途快照、静默等待或完成栅栏、自注销和接收者销毁，且没有
  失效访问或等待自身造成的死锁；
- 强目标绑定与弱/间接目标绑定分别验证：前者在静默前不销毁目标，后者在失效竞争中
  要么取得覆盖完整回调的访问权，要么安全跳过，并按契约报告和清理失效绑定；
- 阻塞处理器触发 drain deadline 后，声明的超时策略不会销毁仍被访问的对象；
- 处理器运行在契约声明的执行上下文，上下文亲和处理器不会被错误调度；
- 支持范围内的并发注册和发布没有数据竞争，并记录长处理器造成的串行阻塞；
- 发布者持有业务锁的测试能发现反向调用、锁顺序冲突和超时；
- 回调内注册、注销和嵌套发布按照禁止、延迟或快照策略得到确定结果；
- 每种可恢复失败策略都覆盖单处理器失败、多处理器部分失败和错误上报再次失败，
  并验证所有观察者仍获得执行机会；致命失败按已声明的宿主隔离策略验证；
- 封闭集合能在构建期或启动期完整校验；开放集合的未知类型和漏注册能被发现；
- 普通 Component 的测试只注入窄发布替身，不需要构造完整全局 Bus；
- 跨 Module 路由清单验证事件所有者、发布方、订阅方、事实建立点、注册位置、
  执行上下文、延迟或阻塞预算、失败与生命周期策略同实现一致。

项目还应使用所选语言和运行时可用的静态分析、资源泄漏检测、并发检测和故障注入
工具，重点覆盖关闭竞争、失效引用、订阅转移和可重入场景。性能测试至少记录处理器
数量、单处理器最坏耗时、并发发布者数量和共享状态竞争，而不是只测空事件吞吐量。

## 定义复用与实例所有权

定义复用、实例所有权和状态共享是不同关系：

```text
定义复用：自包含的 Module / Component 定义 → 多个独立消费方
默认所有权：System 实例 → 可选的 Module 实例 → 可选的 Component 实例
契约依赖：System / Module / Component → 获准依赖的抽象契约
```

规则如下：

- 每个 Module 实例只归一个 System 实例所有；
- Component 实例默认由一个 Module 实例拥有；
- 一个定义可以产生零个、一个或多个实例；
- 定义复用不建立消费方之间的运行依赖；
- 定义复用会建立源码、构建、包版本或供应链耦合，必须显式记录并管理兼容性；
- 定义复用不得携带原消费方的状态、策略、生命周期或资源所有权；
- 跨 System 不直接共享 Module 或 Component 实例。

EventBus 库或包装器可以作为可复用 Component 定义，但复用定义不等于共享运行
实例。Module 私有 Bus 由该 Module 拥有；跨 Modules 的 System Bus 由 System 唯一
拥有，各 Modules 只取得事件类型受限的发布能力和各自的订阅句柄。不同 Systems
不得通过共享一个进程内 Bus 绕过公开契约。第三方库版本、包装器策略和测试基线
属于定义复用产生的供应链与兼容性责任。

线程池、GPU 设备、数据库连接池、事件循环和大型缓存等共享资源由负责其完整
领域的 System 拥有，Modules 只接收窄能力、租约或借用型视图。

同一 System 内确需共享 Component 实例时，必须满足：

- System 是唯一所有者；
- Modules 只接收窄句柄，不取得配置权、销毁权或具体实现身份；
- 实例无状态、不可变，或具有经过验证的线程安全与隔离契约；
- 实例不承载任何 Module 私有的领域可变状态；
- 契约明确并发、失效、回收和关闭顺序。

不得使用全局注册表共享可变 Component、Module 或第三方资源对象。

## 依赖规则

允许：

- System 调用另一个 System 的公开契约；
- System 组织自己的 Modules；
- 同一 System 内的 Modules 通过窄契约形成单向无环依赖；
- Module 组织 Components；
- 同一 Module 内的 Components 依赖获准的抽象契约；
- 多个消费方复用自包含的 Module 或 Component 定义；
- System 在满足安全条件时拥有并借出共享 Component 实例；
- 对等 Systems 通过产品级或外部中立协议进行双向运行时通信，并独立治理同步调用
  环的超时、取消、故障隔离和嵌套深度；
- 宿主通过版本化插件契约和能力清单发现、装载和卸载实现；
- System 契约显式采纳外部标准类型或原生句柄；
- Component 通过自己的窄输出契约向所属 Module 报告类型化 ComponentOutput；
- Module 显式把 ComponentOutput 映射为自己拥有的 ModuleEvent，并通过 Module
  私有 EventBus 同步分发；
- System 使用自己拥有的 EventBus 和 SystemEvent 契约组织跨 Module 的进程内通知；
- 边界感知的私有 Component 依赖事件类型受限的发布 callable 或窄发布端口；
- Module/System 在组装期注册处理器，并由明确所有者保存作用域订阅句柄；
- Module/System 维护完整的进程内路由清单，并把同步调用边纳入环和锁顺序审查；
- 组合根按已经批准的路由执行创建和注册，不自行决定业务响应；
- 跨 System 消息使用独立公开契约与通信 Adapter，具体规则见
  [[集成消息与事件投递设计]]；
- 事件引发的多步骤响应由显式 Workflow 或协调者管理顺序、失败和终止。

禁止：

- System 穿透另一个 System 访问其 Module、Component 或私有类型；
- 跨 System 的 Module-to-Module 依赖；
- 隐藏、双向、成环或面向具体实现的结构性同层依赖；经中立协议治理的双向运行期
  通信不等于这种结构性依赖；
- Component 反向取得 Module 或 System 的对象、实现或生命周期；
- 未经显式采纳的下层或第三方类型、错误模型及生命周期语义泄漏到上层契约；
- 下层决定上层领域流程；
- 使用服务定位器、全局注册表、隐藏回调或字符串主题绕过边界；
- 普通业务代码通过全局单例或静态入口任意访问 EventBus；
- 把完整 EventBus 注入只需要发布单一事件的普通 Component；
- 通过同一个进程内 Bus 直接连接不同 Systems；
- 用广播事件伪装命令、查询、事务或有固定顺序的工作流；
- 透传私有对象、可变引用、超出声明分发期可能失效的借用视图、回调或无治理通用
  字典作为事件负载；
- 依赖处理器注册顺序，或假设同步 EventBus 会自动换线程、排队和并行；
- 持有订阅者可能再次取得的业务锁时同步发布，却没有经过批准的全局锁顺序；
- 在实现未声明支持时，于处理器内注册、注销或递归发布事件；
- 让活动订阅绑定或发布快照访问晚于 EventBus 有效期，或让回调在没有安全所有权、
  有效性检查或静默证明时访问已失效目标；
- 未声明处理器失败传播策略，或静默吞掉注册、共享状态和处理器错误；
- 采用开放事件集合却没有事件类型清单、作用域限制和漏注册测试；
- 直接暴露第三方 EventBus 类型，使所有业务 Components 依赖其实现和生命周期。

运行时调用和数据流不等于架构依赖方向。判断真实关系时必须分别检查源码或契约
依赖、实例所有权、同步可用性、异步因果关系和领域流程决定权，而不能只看函数
调用或事件流箭头。

## 层级判定

| 层级 | 成立依据 | 不是依据 |
|---|---|---|
| System | 完整领域需求、公开契约、领域结果及适用的状态与策略 | 目录大、类型多 |
| Module | 内聚子能力、信息隐藏、独立变化原因 | 文件数量、执行步骤 |
| Component | 单一职责、窄契约、可测试、可替换 | 使用同一库、被调用多次 |

按以下顺序判定：

1. 能否向产品或其他领域独立承诺结果，并定义适用的状态、失败和生命周期语义？
   若是，判为 System；无状态不影响判定；
2. 是否只作为某个 System 的私有实现角色才有意义，并围绕一个变化原因隐藏
   多项协作决策？若是，判为 Module；定义能否复用不影响实例的私有身份；
3. 是否只有一项职责，能通过窄契约独立测试和替换而不改变 Module 语义？
   若是，判为 Component；
4. 不具备独立契约、替换价值或变化原因时，保持为普通实现。

角色数量不由文件、类型、对象或实例数量决定。

## 不变量、默认策略与治理要求

三类规则不得混用：硬不变量在所有合规实现中都成立；默认策略可以被显式、受审查
的边界决策替代；治理要求规定必须留下哪些可验证证据。

### 硬不变量

- **I-01 角色独立**：角色、代码定义、运行实例和物理工程单元彼此区分；角色身份、
  架构可见性和定义复用级别分别判定，定义可以没有运行实例；
- **I-02 唯一所有权**：每个 Module 实例只归一个 System 实例所有；私有 Component
  实例由 Module 拥有，共享 Component 实例由 System 唯一拥有；
- **I-03 契约归属**：每层拥有自己的契约和语义类型；中立协议可以拥有不可变值、
  消息、参与角色、交互状态转换和兼容规则，但不拥有业务实现、运行时可变领域状态
  或生命周期；
- **I-04 边界隔离**：跨 System 的 Modules 与私有 Components 保持隔离；Systems 只
  通过公开 System 契约或获准的中立协议协作，下层和第三方语义不得意外泄漏；
- **I-05 结构与启动无环**：源码或契约直接依赖、实例所有权、强借用和启动先后约束
  显式无环，联合启动约束可拓扑排序；同步可用性单独建模，可以成环，但必须治理
  共同故障、超时、取消和隔离，并禁止无界嵌套同步调用；
- **I-06 下层依赖边界**：同一 System 内的 Module 依赖显式、单向、无环且不穿透
  实现；Component 只依赖获准的抽象契约，不取得提供方实现、实例所有权或生命周期；
- **I-07 决策权向下组织**：上层组织下层，下层不反向决定上层；组合根只负责组装和
  生命周期，不承担领域流程；Workflow/Application System 可以编排但不夺取其他
  Systems 的状态所有权；
- **I-08 复用不共享所有权**：定义复用不等于共享实例、状态或领域所有权，但形成的
  构建、版本和供应链耦合必须被承认；
- **I-09 EventBus 作用域**：EventBus 是可选的进程内同步基础设施 Component，不是
  第四层、流程所有者或服务定位器；Module 私有 Bus 由 Module 拥有，跨 Module Bus
  由 System 拥有，禁止全局单例和跨 System 共享 Bus；
- **I-10 事件事实性**：Event 只能在 FactEstablished 后发布，事件实例及其负载在
  有效期内不可变；契约演进必须有明确兼容策略，独立发布、部署或动态装载的契约必须
  版本化；ModuleEvent、SystemEvent、IntegrationEvent 是所有权/范围分类，
  DomainEvent、TechnicalEvent 是语义分类，两个维度正交且提升不是必经链；
- **I-11 负载安全**：事件负载不得携带可变引用、回调、资源对象、事务对象、发布者
  私有错误或可转移授权能力；临时只读表示只允许在可观察内容和存活期覆盖完整同步
  分发时使用，处理器不得越期保存；
- **I-12 订阅存活**：每个活动绑定都有唯一释放责任方，绑定及发布快照不越过 Bus
  有效期；回调访问的目标状态由静默注销、完成栅栏、安全回调所有权或原子有效性
  检查覆盖，不发生失效访问；失效跳过遵守已声明的失败与清理语义，不能永久静默；
- **I-13 同步边界**：发布沿用调用方执行上下文，不自动异步、并行或迁移上下文；
  处理器顺序不能成为业务正确性契约；
- **I-14 观察失败不改写事实**：可恢复观察者失败不能阻止其他观察者获得执行机会，
  也不能撤销已建立事实；技术分发报告不得充当业务应答；
- **I-15 EventBus 不替代其他机制**：返回值、固定顺序、事务原子性或总体成功使用
  直接契约、Pipeline 或 Workflow；异步、持久化、跨进程和跨 System 保证属于独立
  通信设计；
- **I-16 契约依赖仍存在**：EventBus 只解除发布者与具体订阅者的身份依赖，不消除
  双方对事件契约的源码或运行时契约依赖；
- **I-17 实现语义不泄漏**：语言、对象模型、资源管理、错误和生命周期机制不得成为
  通用模式前提；第三方或语义不匹配的实现通过私有 Adapter 隔离，项目自有实现可以
  直接满足项目契约；
- **I-18 物理形态不改语义**：目录、构建工具、运行实例数量和部署方式不改变模式
  语义；SMC 逻辑视图不替代部署、安全、故障、持久化、实时和性能视图。

### 默认策略

- **P-01 输出直接优先**：Component 默认产生 ComponentOutput；只有形成值得广播的
  已建立事实时，才由 Module/System 可选提升为自己拥有的 ModuleEvent 或 SystemEvent；
- **P-02 事件集合封闭优先**：稳定边界优先采用封闭集合；选择开放集合时必须限制
  作用域，并提供事件清单、注册验证和未知类型策略；
- **P-03 锁外发布**：默认在释放订阅者可能取得的业务锁、资源锁和状态保护器后发布；
  锁内发布例外必须声明全局锁顺序、允许调用边、超时策略，并验证不会反向进入；
- **P-04 分发不可重入**：默认不在分发期间修改本 Bus 订阅表或递归发布；例外必须
  声明处理器快照、增删可见性、嵌套顺序、深度限制和失败语义；
- **P-05 失败隔离**：可恢复处理器失败默认独立上报并继续；采用汇总技术失败时也
  必须先给所有观察者执行机会；
- **P-06 窄能力注入**：普通业务 Component 默认只取得事件类型受限的发布能力，不
  取得完整 EventBus、订阅表或销毁权。

### 治理要求

- **G-01 自上而下设计**：从需求与领域责任产生 System，再划分 Modules 和 Components；
  不得从目录、类型、第三方库或预设清单反推角色；
- **G-02 多视图记录**：分别维护源码/契约依赖、实例所有权与生命周期、同步可用性和
  异步因果图；异步反馈回路明确 correlation、幂等、防循环和终止条件；
- **G-03 可变操作语义**：跨 System 或跨 Module 的可变操作明确原子边界、一致性、
  幂等、并发冲突、部分成功、补偿和恢复责任；
- **G-04 动态扩展治理**：动态发现和插件通过版本化契约、能力清单和明确宿主管理；
- **G-05 路由可审查**：每条同步订阅进入路由清单，记录契约所有者、发布者、订阅者、
  FactEstablished、注册位置、作用域、执行上下文、延迟预算、失败、重入和生命周期
  策略，并纳入依赖环、最长调用链和锁顺序审查；
- **G-06 生命周期可验证**：启动、发布准入、注销线性化、静默回收、drain deadline、
  超时和关闭冲突都有明确行为，错误不能静默吞掉；
- **G-07 复用与共享可治理**：定义复用记录版本和供应链责任；共享实例或资源明确
  唯一所有者、并发、租约、失效与关闭顺序；
- **G-08 验证覆盖风险**：验证 FactEstablished、事件集合、并发发布/注销、锁顺序、
  可重入、失败隔离、关闭竞争和第三方 Adapter，不以空事件吞吐量代替风险验证。
