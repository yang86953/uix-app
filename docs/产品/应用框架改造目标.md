# 应用框架改造目标

[← 返回产品](../产品.md)

## 总目标

将 UIX 改造成便于开发完整原生应用的框架：开发者主要使用 TSX 式 UIX Lang 定义和组合组件，同一份定义可以静态编译或动态加载；`uix-widgets` 提供可复用组件，网络、数据库与 ORM 等通用应用能力由 `uix-app` 统一提供并按需编入。

这是 2026-09-12 确认的产品方向及其完成条件，不是当前版本的能力承诺。阶段结果和执行进度由项目任务维护，实际用法仍以已实现的规范、参考和示例为准。

## 完成条件

| 领域 | 改造后的可观察结果 |
| --- | --- |
| 组件创作 | 新建纯 `.uix` 文件即可定义有类型输入、局部状态、事件和子内容的组件；导入后能复用，不修改框架、不手写逐组件登记或强制附带 Rust 包装。需要原生实现时可增加 `.rs`，使用者的组件接口不变。 |
| 语言与双路径 | UI 是可组合表达式，逻辑和类型不再依赖字符串属性编码。同一份组件及依赖闭包在静态和动态路径具有相同的类型、事件、状态、组合和生命周期语义；静态路径生成原生代码，不以打包解释器冒充 AOT。 |
| 组件库 | 框架不反向依赖官方控件。官方库、第三方库和应用组件使用同一公开机制；普通组合控件由声明表达结构与交互，Rust 保留确有必要的原语、平台和性能实现。 |
| 应用服务 | 网络请求与响应、长连接、上传下载，数据库实体映射、类型化查询、事务和迁移有统一的公开入口、错误、取消与资源关闭合同。UIX 和 Rust 使用同一服务实现，动态宿主只开放已编入的能力。具体协议、数据库后端和依赖选型在实现设计中说明，不将目标写成已有 API。 |
| 按需构建 | 不选动态执行、网络、ORM 或某驱动时，它们不进入消费者构建与交付图；保持框架与组件库两包分工，不因新增服务拆出大量包装包。 |
| 工具与迁移 | check、compile、fmt、query、LSP 与动态装载共享语义和来源位置；错误不静默忽略。旧入口的迁移有具体示例和版本边界，不在已发布版本中静默替换语义，也不无限保留重复实现。 |
| 实际应用 | 使用公开接口完成可运行的综合示例，覆盖组件复用、明暗主题、窄窗口、表单、中文长列表、弹层、网络和持久化；运行错误、卸载、关闭回收及资源消耗有可复核证据。 |

## 推进顺序与共同验收场景

1. **确定基线与共同场景**：保留已实现的样式与两包成果，收口样式工作台作为旧模型行为基线。已有有效像素证据复用，未验的平台不扩大结论。
2. **统一组件与语言最小闭环**：以卡片、计数器和可编辑列表验证定义、导入、状态、事件与子内容；设计可评审的 TSX 式语法及 Rust 绑定合同，贯通同一输入的静态与动态执行。
3. **迁移组件库与工具链**：先迁移代表性组合组件并验证公开第三方组件，再完成受影响组件、工具和示例的迁移；保持样式、焦点、命中、输入和资源生命周期。
4. **接入应用服务**：按真实应用场景落实网络和 ORM 的有界首批后端，再扩充长连接、上传下载及数据协作；每一批明确支持范围和失败行为，不以一个 mock 或键值设置接口代替网络/ORM 完成。
5. **综合交付**：同机同输入核对旧基线与新实现的交互、像素、空闲、切换、缩放、滚动、RSS 和关闭回收，验证独立消费者及实际归档，并同步文档与两端源码。

阶段一不是总体目标的替代品。完整改造不能在只改定位文档、只完成样式、只解析新语法或两条路径分别运行不同组件时宣称完成。

## 决策与范围边界

- 具体语法、底层服务选型与破坏性迁移先形成可评审方案；日常实现与缺陷修复持续推进，重大产品取舍交由用户决定。
- 继续使用原 `uix-app` 和 `uix-widgets` 源码目录；保留现有改动、历史及已发布不可变制品。
- 新版发布、旧消费者整体升级与平台支持扩张分别验收，不由本目标自动宣布完成。当前不自动发布新的 crates.io 版本或改写旧标签。
- 不恢复已停止的主脑、ZCode 调度或定时计划，不因总体目标建立额外执行会话。
