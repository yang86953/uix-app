## 定位

UIX 是一个 Rust 原生跨平台应用框架，目标是让同一套界面与应用逻辑运行在多个平台的原生窗口上。当前主要面向 Windows 与 Linux 桌面应用；macOS 交叉检查不等于已完成原生窗口、GPU 与输入验收，移动端也不是当前交付承诺。

公开源码仓库为 [GitHub](https://github.com/yang86953/uix-app)，按其 MIT 许可证发布。公开说明应体现完整应用框架定位，不能缩减成一种 UI 描述语言加 Rust 运行时；许可与历史发行材料的区别见[交付与许可](交付与许可.md)。

跨平台复用的单位是完整应用，而不只是 Widget 树：UIX 统一应用组合根、生命周期、窗口与事件循环、平台能力、本地数据和运行保障；当前应用自身的业务规则、领域状态与服务编排由 Rust 持有。标准 Scheme 扩展与获准的可移植 UIX 应用模块可以承担扩展自己的业务和动态界面，宿主权威与生命周期仍由 Rust 管理，见[能力与边界](能力.md#软件动态扩展的产品边界)。使用方可以在确有平台差异时消费显式 capability，但不应把窗口、渲染、输入或生命周期分支散落到普通应用逻辑中。

UIX 不把浏览器或 WebView 作为界面运行时。界面推荐用 uix-lang 描述并在正式构建时转换为 Rust；业务逻辑、领域状态、服务调用、导航与应用生命周期使用 Rust 实现。也可以直接使用 Rust 声明式 API 构建界面。框架通过自身图形管线绘制到原生窗口。“全栈”只表示 UI、应用壳和本地数据能力，不包含网络或同步。

**界面与业务开发方式**（产品方向声明）：

- **界面推荐方式**：uix-lang——用 `.uix` 文档描述界面结构、样式、展示数据、界面状态与局部交互；正式构建默认在编译期生成 Rust，不携带语言解释器（规范与边界见 [uix-lang 语言首页](../uix-lang/README.md)）。
- **业务实现方式**：Rust——持有业务规则、领域模型、持久化、网络与平台服务、异步任务、导航/窗口编排和应用生命周期；通过 props、回调或显式根输入向 UI 提供窄契约。
- **支持的界面方式**：Rust 声明式 API——需要直接使用完整组件能力时，也可在 Rust 中构建界面；uix-lang 已登记能力映射到相同的 Rust UI 语义。
- **标准动态扩展方式（已存在公开入口，受 feature 限制）**：标准 Scheme R7RS-small——运行中装载扩展逻辑、命令、事件、服务实现与可选界面；Rust 显式开放宿主能力，扩展拥有自己的状态与算法。详见[目标设计与边界](../架构/app/extensions.md)。

旧 UI 描述只构造和连接界面；新增可移植应用模块可显式声明函数、状态、命令与异步端口，见[应用模块规范](../uix-lang/规范/应用模块.md)。两者不可混称：应用模块不因此获得宿主领域真值、任意 Rust 作用域或未授权服务；UIX AOT/动态是 Scheme 的补充，不替换既有扩展。长期边界见 [UIX Lang 语言边界](../uix-lang/设计/语言边界.md)。

## 框架与组件库定位

**产品定位（2026-09-12）**：在组件体系中，`uix-app` 对应 React 的框架角色，`uix-widgets` 对应 Ant Design 的可复用组件库角色。这个分工是组件创作方式的前提，不仅是把框架源码与控件源码放入两个仓库。

| 层次 | 责任 |
| --- | --- |
| `uix-app`：通用组件框架 | 定义组件、属性、状态、事件、组合与实例生命周期，提供中性界面原语、布局和绘制能力，以及 UIX 编译与动态加载机制。 |
| `uix-widgets`：可复用组件库 | 基于框架公开能力提供按钮、输入、表格、表单等通用控件，以及一致的交互、主题、样式和资源；面向多个应用复用。 |
| 应用及业务组件 | 选择组件库或直接使用框架，组合自己的页面与业务组件；持有具体业务状态、服务、权限和流程。 |

框架不反向依赖某个具体组件库，也不把 Ant Design 的组件名、默认样式或业务策略作为通用组件模型的一部分。应用与第三方库应能通过同一公开组件机制定义和复用自己的组件，不需要修改框架来登记每一种业务组件；具体自动关联和登记方案仍待设计。

组件库的可复用性包括明确的输入、事件、内容插槽与样式扩展点，使应用可以配置、组合和封装组件，而不是复制实现后修改。通用组件不直接绑定某个应用的领域模型、服务实例、业务路由或全局状态；这些依赖经公开输入与回调接入。

纯 `.uix` 与可选 `.rs` 是这套组件机制的创作方式；同一份组件定义支持编译与动态加载是其双路径目标，详见[组件创作与双路径目标](../uix-lang/设计/语言边界.md#01-组件创作与双路径目标)。两者服务于上述框架/组件库分工，不另建两套组件体系。本节是定位与设计要求，不表示统一组件模型已实现。

React / Ant Design 在这里用于说明职责分层与开发体验，不要求引入浏览器或兼容它们的 JavaScript API；UIX 仍是前述 Rust 原生应用框架。

## 目标用户

- 当前需要用 Rust 构建 Windows 或 Linux 桌面应用的开发者
- 希望复用大部分界面与应用逻辑，并把平台差异收敛在框架边界内的团队
- 在乎应用体积和资源消耗
- 想要声明式 UI，但不要 WebView 或 JavaScript

当前不适合作为首选方案的场景：需要复用现有 Web 前端、依赖框架内建网络/云同步，或立即交付移动端。相关边界见[能力与边界](能力.md)和[交付与许可](交付与许可.md)。

## 方案取舍

| 对比方向 | UIX 的选择 | 需要同时考虑 |
|---|---|---|
| Electron | 不捆绑浏览器内核，使用 UIX 自身的布局与绘制管线 | 实际体积、内存和启动速度取决于应用内容、资源、后端与构建配置，不承诺固定倍数 |
| Tauri | 不使用 HTML/CSS/JavaScript 作为界面技术栈，界面由 uix-lang 或 Rust 描述 | 无法直接复用 Web 组件生态；UIX Lang 只映射 UIX 自身语义 |
| Qt 等跨平台原生框架 | 以 Rust 类型和 Cargo 工具链为中心，提供声明式界面与统一平台契约 | UIX 处于早期开发阶段（当前公开 0.0.8），API 和功能可能发生不兼容变化，不承诺生产稳定性；生态、平台覆盖和成熟度需单独评估 |
| Win32 等平台 API | 将平台差异封装在框架边界内，减少应用层条件分支 | 需要精确使用平台专属能力时，仍受 UIX 当前公开能力范围限制 |

## 原则

1. **资源优先**——空闲时进入休眠；重绘、缓存和后台工作必须有明确触发条件与生命周期。
2. **Rust 宿主与标准扩展**——旧 UI 描述在编译时转换为 Rust；可移植应用模块共享语义检查并按需选择 AOT/动态执行。Rust 持有宿主领域真值与生命周期；标准 Scheme 扩展按需承载扩展业务和界面，语言遵循公开标准，宿主 API 独立版本化，不自创私有方言。
3. **原生优先**——上层契约不散落平台条件分支，平台差异由明确边界吸收；平台本身不支持的能力返回可识别错误。
4. **容错可观测**——失败有类型和责任边界，恢复有明确路径，最终失败可以形成报告。
5. **使用方按需编译**——未选择且非传递必需的能力不进入使用方编译图；已选择能力中最终不可达的代码和数据由 release 链接裁剪。运行时关闭能力不能替代编译期裁剪。
6. **最小外部依赖**——新增依赖按真实用途、许可、按需构建和维护收益论证，不为数量下降重写成熟能力；数量不是验收硬目标。历史计数、候选与保留清单见 [依赖治理](../架构/依赖治理.md)。
