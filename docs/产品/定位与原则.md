## 定位

UIX 是一个跨平台原生应用框架，目标是让同一套界面与应用逻辑运行在多个平台的原生窗口上。当前 `0.0.1` 首发范围是 Windows 与 Linux；这一定义不构成对 macOS 或移动端当前完成度的承诺。

UIX 不把浏览器或 WebView 作为界面运行时。应用推荐用 uix-lang 声明界面与应用业务流程，并在正式构建时转换为 Rust；框架负责执行生成代码、组件协调、资源生命周期与原生平台能力。Rust 声明式 API 继续作为框架实现和高级扩展入口，不与 uix-lang 并列为普通应用的主开发路径。框架通过自身图形管线绘制到原生窗口。“全栈”只表示 UI、应用壳和本地数据能力，不包含网络或同步。

**应用开发方式**（产品方向声明）：

- **推荐**：uix-lang——用 `.uix` 文档描述界面、状态与应用业务流程；正式构建默认在编译期生成 Rust，不携带语言解释器（规范与实施边界见 [uix-lang 语言首页](../uix-lang/README.md)）。
- **扩展**：Rust API——实现框架能力、复杂算法、平台与基础设施适配，或承接 uix-lang 尚未登记的临时缺口。已登记语言能力必须映射到确定的 Rust 语义，不能依赖字符串查找、未类型化状态或静默动态回退。

开发模式可以为编辑反馈显式启用动态解析与热重载；它不改变正式构建默认 AOT 的性能契约，也不能让静态入口自动退化为动态执行。应用业务流程与动态模式的目标边界见 [UIX Lang 应用开发语言目标](../uix-lang/变更/应用开发语言目标.md)。

## 目标用户

- 当前需要用 Rust 构建 Windows 或 Linux 桌面应用的开发者
- 希望复用大部分界面与应用逻辑，并把平台差异收敛在框架边界内的团队
- 在乎应用体积和资源消耗
- 想要声明式 UI，但不要 WebView 或 JavaScript

当前不适合作为首选方案的场景：需要复用现有 Web 前端、依赖框架内建网络/云同步、立即交付移动端，或需要以开源许可向外部分发 UIX 本身。相关边界见[能力与边界](能力.md)和[交付与许可](交付与许可.md)。

## 方案取舍

| 对比方向 | UIX 的选择 | 需要同时考虑 |
|---|---|---|
| Electron | 不捆绑浏览器内核，使用 UIX 自身的布局与绘制管线 | 实际体积、内存和启动速度取决于应用内容、资源、后端与构建配置，不承诺固定倍数 |
| Tauri | 不使用 HTML/CSS/JavaScript 作为界面技术栈，界面由 uix-lang 或 Rust 描述 | 无法直接复用 Web 组件生态；UIX Lang 只映射 UIX 自身语义 |
| Qt 等跨平台原生框架 | 以 Rust 类型和 Cargo 工具链为中心，提供声明式界面与统一平台契约 | UIX 尚处于 `0.0.1` 开发阶段，生态、平台覆盖和成熟度需单独评估 |
| Win32 等平台 API | 将平台差异封装在框架边界内，减少应用层条件分支 | 需要精确使用平台专属能力时，仍受 UIX 当前公开能力范围限制 |

## 原则

1. **资源优先**——空闲时进入休眠；重绘、缓存和后台工作必须有明确触发条件与生命周期。
2. **编译优先**——uix-lang 的正式构建转换为 Rust，运行期不引入语言解释器；可静态检查的错误尽量在编译期暴露。开发期动态解析必须显式启用并与发布产物隔离。
3. **原生优先**——上层契约不散落平台条件分支，平台差异由明确边界吸收；平台本身不支持的能力返回可识别错误。
4. **容错可观测**——失败有类型和责任边界，恢复有明确路径，最终失败可以形成报告。
5. **使用方按需编译**——未选择且非传递必需的能力不进入使用方编译图；已选择能力中最终不可达的代码和数据由 release 链接裁剪。运行时关闭能力不能替代编译期裁剪。
