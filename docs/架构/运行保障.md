当前交付事实与活跃差距见[进度 · 运行保障](../进度/运行保障.md)，公开签名与用户写法见[使用 · 运行保障](../使用/运行保障.md)。

## 定位

系统名称统一为 **运行保障（Runtime Assurance）**，覆盖 `core → native/platform → draw → ui/data → app`。它只有一个 Rust 公开面 `uix::diagnostics`，不再增加平行的 `stability`、`recovery` 或 `logging` 根模块。

运行保障有三个职责：

| 职责 | 负责 | 不负责 |
|---|---|---|
| 维稳 | ABI unwind 隔离、owner-thread 汇聚、有界 pending queue、报告容量、递归与错误风暴抑制 | 隐藏可返回的错误、吞掉失败、伪造成功 |
| 纠错 | 按精确 `Errc` 登记恢复处理器，在安全责任线程协调一次恢复尝试 | 内置通用 retry、退避、熔断、GPU 重建、业务补偿或任务运行时 |
| 记录 | typed Error、tracing event/span、最终 ErrorReport、顶层 CrashReport | 第二套 Logger/Sink/Collector、远程上传或普通错误事件总线 |

错误恢复算法始终属于拥有不变量的领域或应用。运行保障只提供登记、选择、隔离和结果归一化，不知道怎样重创 GPU device、重开文件、回滚事务或重建业务状态。

## 单向错误生命周期

```text
操作产生 typed Error
        │
        ├─ 调用方仍能处理/返回 ──────────────► Result<T, Error>
        │
        └─ 到达安全恢复点
                 │
                 ├─ 领域内置恢复成功 ───────► tracing recovery event
                 │
                 └─ Diagnostics::attempt_recovery(error)
                          ├─ Recovered ──────► tracing recovery event
                          ├─ Unhandled(error) ─► 继续返回，或在最终边界 report
                          └─ Failed(error) ────► 继续返回，或在最终边界 report

最终边界 Diagnostics::report(error)
        ├─ 有界、脱敏 ErrorReportStore
        └─ 一条固定 target tracing event

runtime 已不能安全继续
        └─ crash primitive
             ├─ 复用已有 ReportId 或留存一次
             └─ 有界 CrashReport 文件 / stderr；不进入 tracing
```

`report` 不触发恢复，`attempt_recovery` 不自动报告。恢复、传播和最终记录是三个显式阶段，任何日志、快照或终止记录都不能意外执行用户恢复代码。

## 恢复登记

框架和用户使用同一 runtime-scoped registry，并以一个精确 `Errc` 匹配。首版不引入 `ErrorSelector`、字符串规则、wildcard、任意 predicate 或公开优先级：

- `Diagnostics::on_error(code, handler)` 返回 RAII `RecoverySubscription`。
- registration 按稳定登记顺序执行；runtime bootstrap 的框架登记发生在 `App::on_start` 之前。
- `NotHandled` 继续下一个同码 handler。
- `Recovered` 表示 handler 已恢复自己拥有的不变量，立即停止。
- `Failed(recovery_error)` 立即停止，并把原 Error 接到恢复错误的 cause chain。
- handler panic 被 `catch_unwind` 隔离，归一化为 `Errc::TaskAbandoned`，原 Error 仍作为 cause。
- 同线程恢复重入直接返回 `Unhandled`，不形成递归恢复环。

Registry 锁只用于复制匹配 handler 的 `Arc` 列表；执行 handler 前必须释放。Drop registration 只阻止未来选择，已经复制出的 in-flight handler 可以完成一次。注册、注销、快照、tracing 或 report 之间不存在嵌套用户 callback 锁。

`Send + Sync + 'static` 只表示 registration 可随 runtime 安全持有，不授权在任意线程执行。调用 `attempt_recovery` 的当前责任方必须保证线程、资源与生命周期都适合该错误的恢复。

首版恢复是同步的。需要异步 I/O 或跨线程 owner 的领域先投递自己的 typed recovery request；完成后再在 owner thread 产生 `Recovered` 或新的 typed Error。运行保障不创建 executor、future、阻塞等待或 completion queue。

## 领域恢复与用户恢复

执行顺序固定为：

1. 拥有资源的领域先执行自身不可替代的安全恢复，例如 GPU surface 重建、窗口状态纠正或受控软件降级。
2. 领域仍无法处理时，在安全 owner thread 调用共享 registry，让框架其他登记与用户登记按顺序尝试。
3. 全部 `NotHandled` 或恢复失败后，若存在上层 `Result` 路径就继续返回。
4. 已无返回路径的责任方只报告一次；核心不变量已破坏才升级到 crash。

用户 handler 不获得 native handle、GPU device、内部 window owner 或可变平台 trait。它只能使用应用本来就拥有的安全服务和传入的只读 `Error`。需要框架专属对象的恢复必须留在对应 crate-private 领域。

## 平台层全覆盖

公开 `uix::platform::Platform` 方法可以直接返回 `Result`，因此不提前报告，也不自动尝试用户恢复；调用方决定传播、恢复或最终报告。

App 内部使用的 `crate::native` 必须显式接收同一 App runtime 的 `Diagnostics` 句柄，不使用全局实例。跨 FFI、OS 或驱动边界统一复用一个 crate-private `PendingNativeFailureQueue`：

```text
Win32 / ObjC / Wayland / GPU callback
        │
        ├─ catch unwind，选择 ABI 安全返回值
        └─ try_enqueue(PendingNativeFailure)
                 │
                 └─ owner-thread drain
                       ├─ 领域恢复
                       ├─ Diagnostics::attempt_recovery
                       ├─ 能返回则返回 Error
                       └─ 无返回者 report_with_origin 一次
```

Callback 侧硬约束：

- 不调用 tracing subscriber、用户 handler、`Diagnostics::report`、文件 I/O 或网络。
- 不阻塞等待 owner，不持有 native lock 调用未知代码。
- pending payload 只含 typed Error、静态 subsystem / operation、resource kind 与 opaque id；禁止剪贴板、IME 文本、窗口标题、完整路径和用户输入。
- queue 固定容量，使用 non-blocking enqueue；锁竞争或满载只增加原子 dropped 计数。
- owner drain 为一次 overflow 生成一条有界、typed 的汇聚故障记录，随后清零计数；不为每个丢失 callback 制造日志风暴。

各边界的唯一责任点：

| 边界 | 唯一处理点 |
|---|---|
| Win32 `wnd_proc`、ObjC thunk、Wayland callback | 平台 event-loop owner 返回 Rust 后 drain |
| wgpu uncaptured error / device-lost callback | graphics owner 在下一次 `ensure_active` / frame 边界 drain |
| joinable worker | join owner |
| detached worker | worker 入口 wrapper；不存在第二个 join 报告点 |
| Drop / teardown | 正常路径优先显式 `try_shutdown -> Result`；Drop 只处理已无返回路径的最后失败 |

Platform 接入的详细实现边界见[原生平台层](原生平台层.md#运行保障接入)。

## tracing 是唯一日志系统

框架与应用直接使用 `tracing`。UIX 不定义第二套 `Level`、宏、Logger、LogHandler、Record、Sink 或 Layer，也不调用进程全局 `set_global_default`。

普通 `tracing::error!` 不创建 ErrorReport。数据只允许从 typed `Error` 单向投影为 ErrorReport，禁止日志文本反向制造 `Errc::Unknown`。

普通报告 event 使用固定 target `uix::diagnostics`。固定字段至少包括：

- `uix.report_id`
- `uix.error.code`
- `uix.error.severity`
- 有界的 `uix.error.summary`
- `uix.runtime_id`
- `uix.origin.target`
- 可选 `uix.operation`
- 可选 `uix.resource.kind` / `uix.resource.id`

恢复成功使用同一 target 的结构化 INFO event，但不创建 ErrorReport。恢复失败本身不先发 ERROR event；若最终被消费，由最终 ErrorReport event 统一记录，避免双写。

## ErrorReportStore

`ErrorReport` 是从 `Error` 生成的不可变、安全观察投影，不是第二失败类型。它保存报告身份、观察时间、code / severity、有界 summary 与 cause、错误位置与报告位置、typed origin、线程摘要、runtime id 和按策略捕获的 backtrace。

固定安全预算：

- 默认保留 256 条，配置 0 规范化为 1。
- 单条报告最多 32 KiB。
- 单段动态文本最多 2 KiB。
- cause 最多 16 层。
- 文件位置只保留 basename。
- 控制字符被替换；完整路径、标题、输入内容与任意 native payload 不进入报告。

Store 先留存，再在锁外发 tracing event。容量满时淘汰最旧报告，并精确维护 `total_reports` 与 `evicted_reports`。`DiagnosticsSnapshot` 是按 `ReportId` 升序的时点副本。

Subscriber 缺失、过滤或 panic 不影响已留存报告。报告 event 用线程局部 reentrancy guard：嵌套 `report` 仍留存并取得 ID，但抑制递归 event，通过幂次限频 emergency stderr 记录输出故障。

## 生命周期与依赖

每个 App runtime 拥有一个 Clone 的 `Diagnostics` 句柄：

```text
AppRuntime
   └─ Diagnostics
       ├─ AppHandle / user services
       ├─ native platform owner
       ├─ graphics owner
       ├─ draw / UI callback boundaries
       └─ worker owners
```

没有 `Diagnostics::global()`。一个进程 subscriber 可以接收多个 runtime 的 event，但每个 runtime 的 report store、recovery registry、容量与快照相互隔离。

依赖方向固定：

```text
core::Error
    ↓
diagnostics
    ↓
native / draw / ui / data / app 仅持有句柄并调用
```

`diagnostics` 不依赖具体 platform、renderer、UI、data 或 App 恢复算法。CrashReport 需要的 build / OS / GPU 摘要在健康期由外层投影成有界值，不在崩溃路径反向枚举平台。

## Fatal 与 CrashReport

`ErrorSeverity::Fatal` 的普通报告只映射为 ERROR event 加 `uix.error.fatal = true`，不隐式 abort。

只有最外层 runtime owner 确认无法安全继续时才取得一次性 crash ticket：

- 已有 `ReportId` 则引用，不重复留存。
- 未报告的 Fatal 先通过 store primitive 留存一次。
- CrashReport 不调用 tracing、普通 sink、网络、用户 Layer、恢复 handler 或任意 callback。
- 写入使用配置目录、唯一文件名和固定大小上限；失败退回有界 stderr。
- `catch_unwind` 只覆盖 unwind panic；`panic=abort`、访问冲突和其他 native fault 不在首版生成保证内。

## 明确删除的重复轮子

目标完成时直接删除旧 `core::diagnostic` 与 `core::log` 公开/内部实现及其 Collector、ScopedCollector、Logger、Sink、callback token、fatal helper、通用 retry、middleware、circuit breaker 和重复 recovery。不会保留 deprecated alias、桥接 Layer或新旧双写。

日期换算等非诊断通用逻辑必须先移到所属基础模块，再删除旧目录；不能为保留一个通用函数而留下整套旧诊断系统。

## 验证不变量

- 框架和用户可为精确 Errc 登记恢复；顺序、RAII 注销、handler panic 与恢复重入都有测试。
- `attempt_recovery` 不报告；`report` 不恢复。
- 已恢复错误只有一条语义 recovery event，不产生 ErrorReport。
- 一次最终未恢复错误只对应一个 ID、一个 ErrorReport 和至多一个关联 event。
- 没有 subscriber 时 report 仍留存；普通 `error!` 不增加报告数。
- 并发 ID 唯一，容量统计一致；锁内不执行用户代码或 I/O。
- FFI / GPU callback 只投递；owner thread 才执行恢复、tracing 与报告。
- 公开 API 返回的 Error 不被框架提前报告。
- Fatal 普通报告不终止；同一 crash ticket 只执行一次 emergency 路径。
- 公开面不存在第二套 Logger、Sink、Collector、普通错误订阅总线或通用 retry。
