# 使用方按需编译能力映射

> **状态**：ODC-02 首轮盘点 + ODC-03/04/05/06/07 能力落地、图表、表格与导航组件族源码边界、Agent Windows/Linux 构建轴、五种图形公开选择面的正反门禁、两种 Active registry recipe、一批死依赖清理及双目标矩阵（2026-08-05）。本文记录当前源码与 Cargo 清单事实；只有经过独立 fixture、目标过滤的 resolved graph、release 产物或正反类型检查验证的边界才写成已落地结论。

## 盘点口径

主清单是 [`Cargo.toml`](../../Cargo.toml)，公开门面是 [`src/prelude.rs`](../../src/prelude.rs)，系统所有权以各根 Module 的 SMC 说明为准：

| 所有权 | 当前根 Module | SMC 证据 |
|---|---|---|
| 基础契约 | [`src/core`](../../src/core/mod.rs) | SMC-01，模式外基础依赖 |
| 平台与原生后端 | [`src/native`](../../src/native/mod.rs) | SMC-02，私有实现与组装边界 |
| 绘制与渲染 | [`src/draw`](../../src/draw/mod.rs) | SMC-03，graphics System |
| UI 与组件 | [`src/ui`](../../src/ui/mod.rs) | SMC-04，组件与 View 门面 |
| 数据设置 | [`src/data`](../../src/data/mod.rs) | SMC-05，SettingsService |
| 应用与 Agent | [`src/app`](../../src/app/mod.rs) | SMC-06，组合根与自动化 |

本表中的“已门控”只表示存在 feature 或 target `cfg`；是否真的从使用方的 Cargo resolved graph、编译日志和 release 产物中消失，仍由 ODC-01/ODC-07 门禁证明。当前 resolved graph 结论来自 schema v6：Windows 三十一场景使用 `x86_64-pc-windows-gnu`，Linux 最小 check 与 Agent release 两个场景使用 `x86_64-unknown-linux-gnu`；metadata 与 build/check 始终绑定同一个 target，并同时断言 package 存在性、既有 package 上的精确 Cargo feature，以及 `uix` resolve 节点的实际 feature。跨宿主 release 还必须记录 Cargo target linker 覆盖与版本探针；旧 schema v1 的未过滤 package 计数不再承担目标依赖证明，公开 backend 变体的 release 也不冒充生产 registry 或运行时证据。

## 未形成 feature 的基础能力

下列依赖和源码目前仍由主 crate 无条件编译；首轮候选审计已将其归入基础契约，不能在 ODC-01 的 `minimal` fixture 中声称已经排除：

| 基础能力 | 当前无条件依赖 | 主要源码入口 | 所有权结论与复议条件 |
|---|---|---|---|
| 文字布局、栅格化与轮廓 | `ab_glyph` | [`draw/resources/font`](../../src/draw/resources/font/mod.rs) | SMC-03；`FontService` 当前无条件构造唯一的 `AbGlyphBackend`，基础 Typography、测量、栅格化和轮廓均经该后端，现阶段归为基础文字契约；只有先定义无文字或替代后端契约，才可讨论 optional feature 或独立 crate |
| 路径填充与描边细分 | `earcut` | [`draw/geometry/tessellator.rs`](../../src/draw/geometry/tessellator.rs)、[`tests/tessellator_contract.rs`](../../tests/tessellator_contract.rs) | SMC-03；唯一直接调用位于基础 Canvas/path 的严格孔洞快速路径。现有本地 y-band fallback 通过五项填充/描边拓扑契约，但 128 + 128 顶点圆环的 200 次 release 热运行中位耗时由 41.8995 ms 增至 62.0898 ms（+48.2%），每次输出三角形由 256 增至 704（+175%），因此维持基础 Geometry 依赖；只有替代实现同时通过契约且不劣于该基线，才可重新讨论删除 |

`raw-window-handle` 经源码调用点搜索和 `cargo tree -i` 核对后确认只存在一条从 `uix` 发出的无引用直接依赖边，已由提交 `172b7fae` 删除；三十三场景 locked 矩阵均断言其不得重新进入 resolved graph。`bytemuck` 同样没有源码调用点，但依赖树同时存在 `uix → bytemuck` 的无引用直接边和 `uix → image → bytemuck` 的合法传递边；提交 `1d8541cf` 删除前者及无用的 `derive` feature，二十九个未启用图片能力的场景由此完全移除精确 package `bytemuck`，四个图片场景只保留后者，`bytemuck_derive` 则从全部场景消失。`windows-core` 经唯一宏调用点与 Windows/Linux 对照验证后已退出无条件候选清单，继续作为 Windows target 基础依赖。`ab_glyph` 已确认属于当前基础文字实现；提交 `45f65b01` 为 `earcut` 路径建立正确性与手动性能契约，已有 fallback 因显著性能与三角形数量回退而被撤回。至此本轮列示的依赖候选均已闭合；后续继续收缩必须先定义新的公开 capability 或等价替代实现，不能仅按依赖名称机械 optionalize。

## 需要保留的边界事实

1. `d3d11`、`d3d12`、`opengles`、`vulkan`、`metal` 是 backend 轴；公开 `GraphicsBackend` 的五个显式变体分别随同名 feature 收缩，而 native registry 可以保留内部诊断条目。target `cfg` 与 capability feature 必须分别记录，不能把运行时 registry 条目当作已编译实现。resolved graph 必须使用与 build/check 相同的 target 过滤，否则 Windows 结果会混入 Wayland/Unix 条件分支。
2. `settings-serde` 与 `agent-control` 都会启用 `serde_json`；schema v6 的独立 fixture 已证明前者实际选择 `settings-serde` 并解析 `serde + serde_json`，Windows/Linux 两个 Agent 入口都只选择 `agent-control` 并解析 `serde_json` 而不解析设置独占的 `serde`，禁用入口则同步排除 JSON package 与公开方法。后续组合场景仍必须记录 Cargo feature 合并结果。
3. `prelude::QRCode` 已随组件 feature 门控；基础 `Form` 与 `ImageService` 保持导出，但正则 builder 方法及图片字节/路径解码方法随各自 feature 收缩。`RichText` 的实现模块、内容类型、解析/布局辅助、patch、快照与跨节点文字选择分派共同受 `rich-text` 门控；基础与高级图表的实现目录、兼容重导出、全部公开类型、patch、快照和无障碍摘要共同受 `charts` 门控；基础表格、泛型数据表、列/分页模型、patch、快照、render handler 与动态树刷新共同受 `table` 门控；导航组件目录、全部公开类型、patch、快照、无障碍转换与兄弟项刷新共同受 `navigation` 门控。`Image` 的预加载句柄路径继续属于基础 RGBA 契约。其余大量绘制、设置和组件类型仍无条件导出，继续收缩前必须定义哪些导出属于基础契约，哪些应随 feature 隐藏。
4. 在 `x86_64-pc-windows-gnu` 目标过滤口径下，`image`、`qrcode`、精确 package `regex`、`serde_json` 与 `tracing-subscriber` 已从各自未选场景的实际 resolve 节点中消失，精确 package `windows`、`windows-core` 存在且 `wayland-client`、`libc` 缺席；在两个 `x86_64-unknown-linux-gnu` 场景中平台依赖恰好反向。schema v6 另证明 `rich-text`、`charts`、`table` 与 `navigation` 都在各自正向、默认和两个演示场景的 `uix` resolve 节点中存在，在 Windows/Linux 最小与对应禁用场景中缺席；Windows/Linux Agent 入口都只选择 `agent-control`，设置入口只选择 `settings-serde`。Linux Agent 图相对 Linux 最小图新增 `itoa`、`serde_core`、`serde_json`、`zmij`，`memchr` 已由 Wayland 基础图共享，不应重复归因给 Agent。D3D11 单 backend 相对最小入口不新增 registry package，只增加五项 `windows` package feature；D3D12 选择面同样不新增 registry package，只切换六项声明的 Windows API feature；OpenGL ES 只新增 `glow`，Vulkan 只新增 `ash + libloading`，Metal 不新增 registry package。五种选择面均有根 feature 与公开变体的正反证据，但只有 D3D11/OpenGL ES 已接入 Active registry recipe。`raw-window-handle` 已从全部三十三场景消失；`bytemuck` 只在启用 `image` 的四个场景中作为其传递依赖存在，二十九个非图片场景缺席，`bytemuck_derive` 全部缺席。日志对照基础组合本身启用 `regex`，会与订阅器共享部分传递节点，因此只以精确 package 正反断言证明边界。Linux Agent 当前已有目标过滤解析图、代码生成与 release ELF 链接证据，但没有在 Linux 主机运行；D3D12/Vulkan/Metal 仍缺 Active registry、统一薄 RHI 或目标平台运行证据，其余 target 与尚未分区的公开能力不得据此宣称已完成裁剪或交付。
