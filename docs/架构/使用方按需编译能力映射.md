# 使用方按需编译能力映射

> **状态**：ODC-02 首轮盘点 + ODC-03/05/06/07 四批能力落地、一批死依赖清理与 Windows/Linux 双目标矩阵（2026-08-04）。本文记录当前源码与 Cargo 清单事实；只有经过独立 fixture、目标过滤的 resolved graph、release 产物或正反类型检查验证的边界才写成已落地结论。

## 盘点口径

主清单是 [`Cargo.toml`](../../Cargo.toml)，公开门面是 [`src/prelude.rs`](../../src/prelude.rs)，系统所有权以各根 Module 的 SMC 说明为准：

| 所有权 | 当前根 Module | SMC 证据 |
|---|---|---|
| 基础契约 | [`src/core`](../../src/core/mod.rs) | SMC-01，模式外基础依赖 |
| 平台与原生后端 | [`src/native`](../../src/native/mod.rs) | SMC-02，私有实现与组装边界 |
| 绘制与渲染 | [`src/draw`](../../src/draw/mod.rs) | SMC-03，graphics System |
| UI 与组件 | [`src/ui`](../../src/ui/mod.rs) | SMC-04，组件与 View 门面 |
| 数据设置 | [`src/data`](../../src/data/mod.rs) | SMC-05，SettingsService |
| 应用与 Agent | [`src/app`](../../src/app/mod.rs) | SMC-06，组合根与自动化 |

本表中的“已门控”只表示存在 feature 或 target `cfg`；是否真的从使用方的 Cargo resolved graph、编译日志和 release 产物中消失，仍由 ODC-01/ODC-07 门禁证明。当前 resolved graph 结论来自 schema v3：Windows 十一场景使用 `x86_64-pc-windows-gnu`，Linux 最小场景使用 `x86_64-unknown-linux-gnu`；metadata 与 build/check 始终绑定同一个 target。旧 schema v1 的未过滤 package 计数不再承担目标依赖证明，Linux check 也不冒充 release/backend 证据。

## 尚未形成 feature 的候选能力

下列依赖和源码目前仍由主 crate 无条件编译，不能在 ODC-01 的 `minimal` fixture 中声称已经排除：

| 候选能力 | 当前无条件依赖 | 主要源码入口 | 所有权与下一步 |
|---|---|---|---|
| 字体与文字布局 | `ab_glyph` | [`draw/resources/font`](../../src/draw/resources/font/mod.rs) | SMC-03；先确认 App 启动和基础 Typography 是否共同需要，再决定 optional feature 或独立 crate |
| 字体轮廓与路径几何 | `earcut`、`bytemuck` | [`draw/geometry/tessellator.rs`](../../src/draw/geometry/tessellator.rs)、绘制 backend | SMC-03；可能是绘制基础共享依赖，不能直接按组件 feature 切断 |

`raw-window-handle` 经源码调用点搜索和 `cargo tree -i` 核对后确认只存在一条从 `uix` 发出的无引用直接依赖边，已由提交 `172b7fae` 删除；十二场景 locked 矩阵均断言其不得重新进入 resolved graph。`windows-core` 经唯一宏调用点与 Windows/Linux 对照验证后已退出无条件候选清单，继续作为 Windows target 基础依赖。`ab_glyph`、`earcut`、`bytemuck` 等剩余依赖同时出现在绘制基础路径中；它们是否可拆，必须以“关闭候选能力后最小 fixture 仍能 clean release build”为前提，不能仅按依赖名称机械 optionalize。

## 需要保留的边界事实

1. `d3d11`、`d3d12`、`opengles`、`vulkan`、`metal` 是 backend 轴；target `cfg` 与 capability feature 必须分别记录，不能把运行时 registry 条目当作已编译实现。resolved graph 必须使用与 build/check 相同的 target 过滤，否则 Windows 结果会混入 Wayland/Unix 条件分支。
2. `settings-serde` 与 `agent-control` 都会启用 `serde_json`；Cargo feature 合并后，单独 fixture 的 resolved graph 必须记录实际合并结果。
3. `prelude::QRCode` 已随组件 feature 门控；基础 `Form` 与 `ImageService` 保持导出，但正则 builder 方法及图片字节/路径解码方法随各自 feature 收缩。`Image` 的预加载句柄路径继续属于基础 RGBA 契约；其余大量绘制、设置和组件类型仍无条件导出，继续收缩前必须定义哪些导出属于基础契约，哪些应随 feature 隐藏。
4. 在 `x86_64-pc-windows-gnu` 目标过滤口径下，`image`、`qrcode`、精确 package `regex` 与 `tracing-subscriber` 已从各自未选场景的实际 resolve 节点中消失，精确 package `windows`、`windows-core` 存在且 `wayland-client`、`libc` 缺席；在 `x86_64-unknown-linux-gnu` 最小场景中平台依赖恰好反向。`raw-window-handle` 已从全部十二场景消失。日志对照基础组合本身启用 `regex`，会与订阅器共享部分传递节点，因此只以精确 package 正反断言证明边界。Linux 当前只有 check 证据，其余 target、backend 与候选依赖不得据此宣称已完成裁剪或交付。
