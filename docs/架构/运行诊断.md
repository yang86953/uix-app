# 运行诊断

[← 返回架构 索引](../架构.md)

> 分类：运行诊断
> 权威范围：框架与应用共用的错误观察、结构化日志、最终边界与崩溃不变量

交付事实与活跃差距由[运行诊断进度](../进度/运行诊断.md)记录。

## 定位与边界

系统名称统一为 **运行诊断（Diagnostics）**，公开模块为 `uix::diagnostics`。它覆盖 `core → native → draw → ui/data → app`，框架代码与应用代码使用同一规则：

- `Error` / `Errc` / `Result<T, Error>` 表达可返回、可处理的失败；
- `tracing` event / span 表达结构化运行记录；
- `ErrorReport` 保存已被最终责任边界消费、无法再以 typed `Error` 交给下一层的失败；
- `CrashReport` 是顶层无法安全继续时生成的内部崩溃产物。

诊断层不接管业务重试、熔断、GPU 恢复、窗口隔离决策、任务调度、指标系统或远程上传。所属域先决定返回、恢复、降级、隔离或终止；诊断只记录必要事实。

## 日志直接复用 tracing

日志、span、target、字段、过滤和输出扩展直接采用 [`tracing`](https://docs.rs/tracing/latest/tracing/)：

- 框架与应用直接使用 `tracing::{trace, debug, info, warn, error, span}`；
- 不定义第二套 `Level`、日志宏、`Logger`、`LogHandler`、`Record`、`Sink` 或 UIX Layer；
- 文本、JSON、文件轮转和外部监控由宿主的标准 subscriber / Layer 负责；
- UIX 库不调用全局 [`set_global_default`](https://docs.rs/tracing/latest/tracing/subscriber/fn.set_global_default.html)；可执行程序安装 subscriber，嵌入场景沿用宿主已经建立的 subscriber；
- UIX 不承诺宿主 writer 的队列、丢弃或 flush 语义，只要求生产配置有界且不阻塞关键线程。

`ErrorSeverity` 是故障分类，`tracing::Level` 是观察记录级别，两者不合并。普通 `tracing::error!` 只是日志，不创建 `Error` 或 `ErrorReport`。

## 三条明确路径

```text
普通运行记录
framework / application
        └─ tracing event / span ──► ambient subscriber

普通错误报告
Result<T, Error>
        ├─ 仍可返回或已恢复 ──► 不 report；按需写 tracing
        └─ 最终边界消费错误
                  └─ Diagnostics::report(error)
                          ├─ 有界、脱敏 ErrorReportStore
                          └─ 一条固定 target 的 tracing event

顶层崩溃
fatal Error / 顶层 unwind panic
        └─ 内部 crash primitive
                ├─ 有界、脱敏 ErrorReportStore
                └─ emergency CrashReport ──► 有界文件 / stderr
                                             不调用 tracing subscriber
```

普通 `report` 与 crash 路径复用内部 store primitive，但语义不同：

- 普通 `report` 先留存，再发一条 `target = "uix::diagnostics"` 的 event；
- crash 路径留存后直接写 `CrashReport`，不调用 tracing 或任何用户 Layer；
- crash coordinator 若已持有 `ReportId`，复用该报告，不再次留存；
- 日志过滤、subscriber 缺失或输出失败不得影响 ErrorReportStore。

数据只从 typed `Error` 单向生成 `ErrorReport`。禁止日志反向制造 `Errc::Unknown`，也禁止 ErrorReportStore 再调用另一套 Logger。

## Error 与 ErrorReport

`Error` 继续作为唯一失败值，保留错误码、严重度、稳定消息、创建位置和 source chain。传播期间只补充 typed 因果，不先格式化为字符串再重建。

`ErrorReport` 不是第二错误类型，而是从 `Error` 生成的不可变、安全观察快照。它至少保存：

| 字段 | 契约 |
|---|---|
| `ReportId` | 仅在一个 `Diagnostics` 生命周期内唯一且单调 |
| `observed_at` | 最终边界观察时间 |
| code / severity | 原 typed 分类 |
| message / causes | 保留逐层 code / severity，清理控制字符、逐项截断并受总字节与最大 cause 深度约束 |
| error site / report site | 错误创建位置与最终报告位置 |
| origin | 框架内部有界 typed 来源：subsystem、静态 operation、可选 resource kind / opaque id |
| thread / runtime id | 线程摘要与不透明 runtime 身份 |
| backtrace | 按固定配置可选、同样有大小上限 |

Store 不保留任意长度的原始 `Error` 文本。若 source chain 超过预算，报告带 `causes_truncated`；若单条报告超过总预算，按稳定顺序截断，不能无界分配。应用仍不得把 token、密码或文件内容写入 Error 消息，因为通用清洗无法判断任意业务字符串的真实敏感性。

内部 `ReportOrigin` 是固定 schema，不进入公开构造 API。FFI / GPU callback 先生成包含 Error 与 origin 的有界 owned pending failure，owner thread 再通过 crate-private 报告入口生成 ErrorReport。公开 `report(Error)` 使用 application origin；应用的业务关联继续放在现有 tracing span，不新增 context builder。

首版不做消息哈希去重：每次最终报告得到独立 `ReportId`。Store 使用固定容量淘汰最旧报告，并精确记录 `total_reports` 与 `evicted_reports`。`DiagnosticsSnapshot` 是调用时点不可变快照，报告按 `ReportId` 从旧到新排列。

## 报告时机

同一 Error 遵循“返回、包装、最终消费后报告”规则，禁止每层 `log + return Err`。

| 边界 | 规则 |
|---|---|
| 公开 API | 预期失败返回 `Result`；框架不替调用方提前报告 |
| 探测 / 重试 | 候选失败只记 Trace/Debug；耗尽后若仍向上返回，只包装 Error；本层最终消费时才报告 |
| 已恢复 / 已降级 | 所属域写语义明确的 tracing event，不创建 ErrorReport |
| 用户回调 | 仅在声明为可隔离的边界 catch unwind；若框架消费该失败而不再返回，则在 owner thread 报告一次 |
| FFI / OS callback | unwind 不跨 ABI；只捕获并投递有界 owned 故障，由 owner thread 报告，不在回调线程执行 subscriber |
| GPU callback | 保存 reason 与设备身份并投递给 graphics owner；恢复失败且错误被本层消费时报告一次 |
| joinable worker | 只由 join owner 观察和报告；worker 入口不重复报告 |
| detached worker | 只由入口 wrapper 承担最终报告；不存在第二个 join 报告点 |
| event loop / frame | 可返回则返回，可恢复则记录；核心不变量损坏才进入顶层 crash |

`report` 会同步触发 ambient subscriber，因此不得直接用于 FFI、OS 或 GPU 驱动 callback。那些边界复用现有 owner-thread 调度设施，不为诊断再建任务运行时或阻塞队列。

## 严重度与终止

普通报告 event 使用固定映射：

| `ErrorSeverity` | tracing event |
|---|---|
| `Info` | `INFO` |
| `Warning` | `WARN` |
| `Error` | `ERROR` |
| `Fatal` | `ERROR` + `uix.error.fatal = true` |

构造或调用公开 `report` 报告 Fatal 都不会隐式 abort。只有最外层 runtime owner 确认状态不能安全继续后，才进入内部 crash primitive。已被安全隔离的 panic 不应继续标为 Fatal。

普通报告 event 使用固定 target `uix::diagnostics`，发布 `uix.report_id`、`uix.error.code`、`uix.error.severity`、有界脱敏的 `uix.error.summary`、不透明 `uix.runtime_id`，以及框架内部 origin 的 `uix.origin.target`、`uix.operation` 和可选 resource 字段。公开应用报告没有 operation/resource；业务关联继续放在当前 tracing span，不新增动态 target/context builder。

## 生命周期

每个 App runtime 持有一个 `Diagnostics` 实例并向各层传递 Clone 句柄；没有 `Diagnostics::global()`。未配置时 App 创建安全默认实例，应用可用 `AppHandle::diagnostics()` 取得同一个句柄。独立测试或非 App 场景可直接创建隔离实例。

进程级 tracing subscriber 与 runtime-scoped Diagnostics 是两种所有权：

- 一个宿主 subscriber 可以接收多个 runtime 的日志；固定 `uix.runtime_id` 字段用于区分报告；
- 每个 runtime 的 ErrorReportStore、容量和快照相互隔离；
- UIX 不在 runtime 启停时替换全局 subscriber；
- 输出 writer、worker guard 与 flush 生命周期归宿主，不进入 Diagnostics API。

目标公开面只包含 runtime 句柄、配置、报告身份、安全错误报告与不可变快照；精确签名由[使用文档](../使用/诊断.md#公开-api)定义。

旧 `Collector` / `ScopedCollector`、Logger/Sink SPI、callback token、通用 retry/middleware/recovery、panic hook、crash writer 与 abort helper 都不是目标公开面。

## 并发与输出故障

- ErrorReportStore 有固定条数和单报告字节预算；`report` 可从普通应用/worker 线程并发调用。
- Store 临界区不执行文件或网络 I/O，不调用用户 callback，不调用 tracing。
- 普通 `report` 先完成留存，再在锁外发 event；subscriber 的过滤不影响快照。
- event 调用对 subscriber 的 unwind panic 做隔离；报告仍保留并走一次限频 emergency stderr。它不能防止 `panic=abort` 或一个阻塞的 subscriber。
- event 发射使用线程局部 reentrancy guard。若宿主 Layer 在处理报告 event 时再次调用 `report`，嵌套 ErrorReport 仍有 ID 并留存，但不再次进入 subscriber，只写一次限频 emergency stderr；快照标记该 event 被抑制。宿主 Layer 禁止从自身回调重入 `report`。
- subscriber / writer 是否异步、有界、丢弃或持久化完全由宿主配置；`DiagnosticsSnapshot` 不伪造宿主 dropped 计数。
- 快照只公开 `total_reports`、当前 retained 数和 `evicted_reports`，不提供同步订阅、`clear`、`flush` 或动态容量修改。

## Panic 与 CrashReport

UIX 首版不安装进程全局 panic hook。可恢复的 unwind panic 只在用户回调、worker、FFI wrapper 和 `App::run` 顶层等明确所有权边界捕获：

- 可安全隔离：转为 Error，在 owner thread 普通报告；
- runtime 已不安全：取得该 runtime 的一次性 crash ticket，直接走 crash primitive；
- 已有 ErrorReport：CrashReport 引用既有 `ReportId`，不重复报告。

CrashReport 允许有上限的同步文件或 stderr 写入，因为它是终止前 emergency 路径；它不得调用普通 subscriber、网络、用户 Layer 或任意 callback。build、OS 与必要 GPU 摘要必须在健康运行期预先缓存，崩溃时不重新枚举系统或驱动。文件使用配置目录、唯一名称和大小上限，不覆盖当前工作目录固定文件。

`catch_unwind` 只覆盖 unwind panic。`panic=abort` 最多由宿主/默认 hook 输出，访问冲突等 native fault 交给 OS crash integration；UIX 首版不声称这些一定生成 CrashReport。UIX 只保证自身 runtime crash primitive 对同一 crash ticket 执行一次，不能保证宿主 hook 不额外输出或终止。

## 隐私

- 框架 Error、tracing event 与 CrashReport 永不记录密码、token、secret、剪贴板、输入内容或文件内容。
- 完整路径、窗口标题和用户文本默认省略、散列或截断。
- ErrorReport 使用固定清洗与预算，不接受可关闭的脱敏开关或用户 redactor callback。
- 应用自己的 Error 消息与 tracing 字段遵守同一输入约束；外部 Layer 的导出政策由宿主负责。
- 远程导出默认不存在；CrashReport 只保存 ErrorReport 与预缓存的最小运行信息，不抓取普通应用日志或原始内存。

## 验证不变量

- 没有 subscriber 时普通 tracing 无输出，但 `report` 仍能留存 ErrorReport。
- 一次非重入普通 `report` 生成一个 ReportId、一个 ErrorReport 和一条关联 event；重入报告留存但抑制递归 event。
- 普通 `error!` 不增加 ErrorReport 数量。
- crash 路径不调用 tracing；已有 ReportId 时不重复留存。
- 并发身份唯一，容量淘汰与 total / retained / evicted 一致。
- 用户和 `uix::*` 日志进入同一宿主 subscriber，ErrorReportStore 按 runtime 隔离。
- FFI / GPU callback 只投递，joinable worker 只在 join owner 报告。
- Fatal 的普通报告不终止；顶层 crash primitive 对同一 ticket 只执行一次。
- 公开面中不存在第二套 Logger、Sink、Collector、Layer 或通用 retry。
