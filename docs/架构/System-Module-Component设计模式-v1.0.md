# UIX App：System / Module / Component 应用映射 v1.0

[← 架构索引](../架构.md)

> **接口**：适用于把通用 SMC 定义应用到 UIX 的领域边界、实现单元、运行时所有权和依赖方向。通用 System、Module、Component 角色及不变量以共享工程资料为唯一权威；本文只持有 UIX 的具体应用映射，系统清单由[系统列表](系统列表.md)持有，迁移状态由[进度索引](../进度.md)及[运行保障证据](../进度/运行保障.md)持有。依赖：[产品](../产品.md)。

## 目标

本模式从产品需求自上而下推导职责，把领域公开契约、私有实现分解和可替换行为分开。它同时约束四类关系，禁止用其中一种掩盖另一种：

| 关系 | 回答的问题 |
|---|---|
| 设计分解 | 一项职责属于哪个 System、Module 或 Component |
| 代码依赖 | 哪一层可以在编译期引用哪一层的契约 |
| 运行时所有权 | 谁创建、持有、销毁实例和状态 |
| 定义复用 | 同一个 Component 定义可否被多个 Module 分别实例化 |

目录、crate、Rust module、trait 或 struct 都不是架构层级本身。先确定角色和关系，再选择代码落点。

## System

System 是一个完整领域的唯一公开边界，向外提供该领域的稳定能力。

System 必须：

- 持有领域状态、策略、资源和生命周期；
- 选择、创建并持有自己的 Module；
- 编排多个 Module 共同完成的流程；
- 只通过其他 System 的公开契约建立跨系统依赖；
- 将内部实现类型、第三方类型和底层错误收敛为自身契约。

System 之间的依赖必须显式、有向、无环。回调、事件订阅、异步任务、弱引用和延迟调用都属于真实依赖，不能因调用方向不直观而从依赖图中省略。

System 不是所有实现的合集，也不是全局服务定位器。它对外暴露领域能力，不暴露内部 Module 的实例、目录结构或选择结果。

## Module

Module 是某一个 System 私有的内聚实现单元，用于隐藏一组共同变化的策略和状态。

每个 Module：

- 只归属于一个 System；
- 由所属 System 创建、持有和销毁；
- 只实现所属 System 分配的职责；
- 可以组合多个 Component；
- 默认不进入公开 API，也不成为跨 System 依赖目标。

同一 System 内的兄弟 Module 不得相互发现、引用、持有或调用。需要跨 Module 协作时，由 System 读取一个 Module 的结果，转换为自身契约，再传给另一个 Module。

```text
调用方
  → System 公开契约
      ├─ Module A → Components
      └─ Module B → Components

禁止：Module A → Module B
```

这一规则同样适用于事件、回调和异步通道。把直接调用改成全局总线并没有消除依赖。

## Component

Component 是单一职责、可独立替换的原子行为单元。Rust 中通常表现为小型 `struct`、`enum`、窄 `trait` 或纯函数集合。

Component：

- 可以私有使用标准库和第三方库；
- 只声明完成职责所需的最窄能力；
- 不依赖某个具体 Component 的身份；
- 不依赖 Module 或 System；
- 由消费它的 Module 创建或接收，并由该 Module 持有实例。

Component 的定义可以横向复用，但实例、可变状态和生命周期仍归各自的消费 Module。不得让多个 Module 共享一个可变 Component 实例来形成隐式耦合。

## 契约归属

每一层拥有自己的输入、输出和错误语义。

| 边界 | 契约责任 |
|---|---|
| System | 领域公开能力、跨系统依赖、稳定错误和生命周期 |
| Module | System 内部用例、私有数据转换和局部失败 |
| Component | 单一行为所需的最窄输入、输出和能力 |

下层结构体、第三方句柄、内部错误枚举和借用期限不得穿透上层边界。转换发生在拥有该边界的一层。

Rust 实现遵循以下约束：

- 用 `struct` 组合表达所有权，不用 trait 模拟基类；
- 用策略 trait 抽象可替换行为，外层只依赖必要能力；
- 默认采用泛型和静态分派，只在确有运行时替换需求时使用 `dyn Trait`；
- `Arc`、`Weak`、锁和通道只能由明确的共享所有权、弱生命周期或并发契约引入；
- 跨线程契约显式声明 `Send + Sync`，线程亲和资源不得被包装后伪装成可跨线程；
- 生产路径使用 `Result<T, E>` 传播失败，不用 `unwrap()` 或 `expect()` 隐藏非法状态。

## 共享资源

昂贵或受限资源由 System 持有，例如设备、线程池、字体数据库或原生连接。Module 只获得完成职责所需的窄能力、租约或句柄。

资源不是第四层，也不能成为全局入口。System 负责建立和销毁资源、分配访问能力、定义并发与恢复策略，并把资源失败转换为领域错误。

## 组合根

最终应用拥有组合根。组合根选择需要启用的 System，注入跨 System 契约，并控制进程级启动和关闭顺序。

框架不得提供一个固定的“全系统聚合对象”作为所有调用的必经入口。应用可以按场景组合不同 System；未启用的 System 不应因隐藏注册或全局初始化而存在。

## 强制不变量

1. 角色从需求和职责推导，不从现有目录反推。
2. 每项领域公开能力只有一个 System 负责。
3. System 持有自身状态、策略、资源和生命周期。
4. System 只依赖其他 System 的公开契约。
5. System 依赖图显式、有向且无环。
6. 回调、事件和异步关系计入依赖图。
7. 每个 Module 只属于一个 System。
8. Module 默认是所属 System 的私有实现。
9. 兄弟 Module 之间没有代码依赖或运行时发现。
10. 跨 Module 流程只由 System 编排。
11. Module 持有并组合自己的 Component 实例。
12. Component 只承担一个可独立验证的职责。
13. Component 不依赖 System、Module 或其他 Component 的身份。
14. Component 定义可以复用，实例和可变状态不跨 Module 共享。
15. 各层拥有并转换自己的类型、错误和生命周期。
16. 第三方类型和底层句柄不泄漏到上层公开契约。
17. 共享资源由 System 持有，Module 只获得窄能力。
18. 服务定位器、全局注册表和全局可变状态不得隐藏依赖。
19. 组合根属于最终应用，不属于某个可复用 System。
20. 临时兼容层必须有删除条件，不能升级为长期架构。

## 评审顺序

1. 明确产品行为、失败边界和生命周期。
2. 指定唯一负责的 System 及公开契约。
3. 按共同变化原因划分私有 Module。
4. 提取单一职责、可替换的 Component。
5. 分别画出代码依赖图和运行时所有权图。
6. 检查兄弟 Module 是否存在直接或隐藏依赖。
7. 检查类型、错误、资源和并发语义是否在正确边界收敛。
8. 用替代实现和失败路径验证边界。

任何一项不变量被破坏时，应修正职责或依赖，而不是新增聚合门面、全局注册表或透传接口。
