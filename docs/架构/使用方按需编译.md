# 使用方按需编译

[← 返回架构索引](../架构.md)

> **接口**：声明 UIX 作为依赖进入使用方应用时的构建裁剪契约。依赖：[定位与原则](../产品/定位与原则.md)、[系统列表](系统列表.md)。导出：实施状态 → [Vikunja 项目 4](https://yang-server.tail9d5559.ts.net:3456/projects/4)。

## 目标边界

本目标约束的是**框架使用方的应用构建**，不是 UIX 仓库自身的增量编译速度。

“只编译使用的部分”分为两层：

1. 使用方未选择、且不被已选择能力传递依赖的 UIX 能力，不进入 Cargo 编译图，其专属源码与第三方依赖不参与编译。
2. 使用方已选择能力中，最终没有被应用入口触达的函数、静态数据和实现，不进入 release 目标程序。

被已选能力正常依赖的共享基础设施属于“实际使用”。本契约不承诺移除维持该能力正确运行所必需的传递代码。

## “使用”的判定

Cargo 在编译使用方源码前就必须解析依赖和 feature，因此不能仅凭 Rust 文件中是否写了某个类型名，自动决定是否编译依赖 crate 的某个能力。UIX 使用以下两类信号：

| 粒度 | 使用判定 | 裁剪手段 |
|---|---|---|
| 能力级 | 使用方在依赖声明中显式选择 capability feature；或该能力是所选 feature 的传递必需项 | Cargo feature、`optional` 依赖、目标平台 `cfg`；必要时拆成独立 crate |
| 符号级 | 代码从应用入口可达 | release LTO、链接器 section garbage collection 与 Rust 单态化 |

因此，feature / crate 边界负责“根本不编译”，链接器负责“编译过但不进入最终程序”。只配置 release LTO 不能满足第一层目标；只在运行时关闭能力也不能满足任一层目标。

## 能力分区

能力边界遵循以下顺序建立：

1. **最小基础**：稳定身份、错误、必要几何值等被多数能力共享且体积有限的基础契约。
2. **平台与图形后端**：只编译目标平台以及使用方选择的 backend；未选 backend 的 SDK、适配层和专属依赖不得进入编译图。
3. **System 能力**：data、Agent、无障碍、图像解码、富文本等可独立关闭的能力拥有独立 feature 或 crate 边界。
4. **组件能力**：会引入明显源码量、泛型单态化或第三方依赖的复合组件独立裁剪；小型且仅依赖 UI 基础的组件可以共享较细的组件包，再由链接层移除不可达符号。
5. **聚合入口**：允许提供显式的便捷聚合 feature，但不得把“完整能力集”伪装成最小默认集。

feature 依赖必须服从 [System 依赖有向无环图](系统列表.md#候选领域边界)，不能借 feature 建立运行时代码中禁止的反向依赖。crate 拆分是编译隔离手段，不改变 System / Module / Component 的领域所有权。

当前能力边界以 [`Cargo.toml`](../../Cargo.toml) 的 feature、optional dependency 与 target `cfg` 为准；正确性只由仓库测试覆盖，不维护独立构建矩阵或报告。

## 公开 API 契约

- `uix::prelude` 和各 System 门面只重导出本次构建已启用的能力。
- 引用未启用能力时必须得到稳定、可理解的编译期错误；文档应指出需要启用的 capability feature。
- feature 必须保持加法语义，以适应 Cargo 在依赖图中的 feature 合并；启用一个能力不能静默关闭另一个能力。
- 平台 `cfg` 与 capability feature 是两条独立轴：非目标平台代码由 `cfg` 排除，目标平台上的可选能力由 feature 排除。
- 公开 `GraphicsBackend` 只导出当前构建启用的 backend 变体；关闭 feature 后，使用方必须在编译期失去对应显式选择入口。
- backend 的运行时自动选择只能在已经编入的候选集合内发生，不能让未选 backend 重新进入构建；native registry 可以保留未启用或未实现条目用于内部诊断，但这种条目不构成使用方 capability。
- backend 专属的内部 adapter 构造、recipe 能力构造、遮挡变体与 RHI resize helper 必须服从同一 feature / target 边界；`test` 与 `test-harness` 只能按验证需要保留对应 helper，不能让生产无 backend 构建重新取得这些实现。

目标依赖形态如下；示例使用当前公开的 OpenGL ES 与图片编解码 feature：

```toml
[dependencies.uix]
path = "../uix-app"
default-features = false
features = ["opengles", "image-codecs"]
```

## 何时拆 crate

同一 `rustc` crate 内只有被 `#[cfg]` 排除的 module 才能避免解析、类型检查和代码生成。出现以下任一情形时，应把能力拆成独立 crate，而不是继续扩大主 crate：

- 能力有体积明显的专属依赖，关闭后仍出现在 `cargo tree -e features` 中。
- 能力源码较大，即使最终链接可裁剪，clean build 仍承担明显解析、类型检查或代码生成成本。
- feature 组合让公开面产生大量条件分支，难以通过测试覆盖。
- 该能力有清晰稳定的所有权边界，拆分不会泄漏私有 Module 或破坏 SMC 依赖方向。

## 测试契约

- 新增或调整 capability feature 时，必须补充单元或集成测试，覆盖公开入口启用与关闭后的行为。
- backend 与 target 条件必须由对应平台测试覆盖；未运行的平台只记录为未测试，不生成独立报告。
- 聚合能力、公开 API 与运行时选择都通过仓库测试判断，不维护 fixture 矩阵、产物对比或采集器。
- 具体阶段、当前差距和测试状态由 [Vikunja 项目 4](https://yang-server.tail9d5559.ts.net:3456/projects/4) 持有。

## 非目标

- 不承诺 debug 产物与 release 产物具有相同大小。
- 不以源码 import 扫描、宏猜测或运行时配置替代 Cargo 能力选择。
- 不删除已选能力正确运行所必需的共享基础设施。
- 不为追求极端 feature 数量而把每个小函数或无专属依赖的小组件拆成独立 crate。
