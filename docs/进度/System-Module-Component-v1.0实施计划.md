本计划取代“按现有目录直接搬运”的重构方式。现有目录和类型仅用于定位遗留实现，不自动成为目标 Module 或公开契约。

## Rust 落地规则

- System 的公开契约放在稳定、可导航的 Rust module 中；实现 Module 默认使用私有或 `pub(crate)` 可见性。
- Module 不能通过 `pub use`、容器查询、事件总线或 trait object 绕过兄弟隔离。
- System 构造函数负责选择和注入 Module；Module 构造函数负责选择和持有 Component。
- 默认使用泛型表达编译期策略；只有运行时确需替换时使用 `Box<dyn Trait>` 或 `Arc<dyn Trait>`。
- 不用 `clone()` 逃避所有权设计；共享所有权和锁必须在架构文档中说明原因。
- 每个迁移切片先冻结公开契约，再移动实现，最后删除旧入口。
- 兼容适配器只能存在于边界，并必须记录调用方、删除条件和目标阶段。

## 单个 System 的迁移流程

1. 冻结公开行为、错误语义和生命周期。
2. 盘点同步调用、回调、事件、异步任务、资源和线程边界。
3. 定义 System 公开契约并固化依赖方向。
4. 按共同变化原因划分私有 Module。
5. 从 Module 内提取窄 Component，明确实例所有权。
6. 将跨 Module 流程上移到 System 编排。
7. 收敛底层类型、第三方类型和内部错误。
8. 迁移调用方并删除不再需要的聚合入口。
9. 更新架构、使用和进度证据。
10. 通过定向验证后再开始下一个 System。

`core` 暂作为跨 System 的基础值与错误契约审计，不直接按有状态 System 迁移。若后续发现其拥有独立领域状态、策略和生命周期，再通过架构评审升级为 System；否则保持模式外的基础依赖。

## 首个切片：Diagnostics

目标结构由 Diagnostics System 对外提供报告、查询和恢复契约，并私有持有至少以下职责单元：

- 报告存储 Module；
- 恢复协调 Module；
- 配置与去重策略 Component；
- 时间、日志或持久化等窄能力 Component。

完成条件：

- 调用方不接触报告存储、恢复注册表或内部锁；
- 两个私有 Module 不相互调用，由 Diagnostics System 编排；
- 错误、容量、去重和恢复生命周期边界明确；
- 公开行为与现有使用文档一致；
- 旧聚合实现和临时入口有明确删除记录。

## 验证门槛

每个切片至少执行：

```text
cargo fmt --check
cargo clippy --all-targets -- -D warnings
```

涉及公开 API、跨 System 依赖或组合根时，验证证据必须记录命令、结果和对应迁移项；不能用旧实现仓库的结果替代 Rust 证据。

## 完成定义

一个 System 只有同时满足以下条件才标记完成：

- 公开契约、私有 Module 和 Component 所有权可从文档与代码对应；
- 兄弟 Module 无直接或隐藏依赖；
- 跨 System 图无环且只引用公开契约；
- 下层类型、错误和资源未泄漏；
- 兼容层已删除或有明确的剩余调用方和删除期限；
- 格式与静态检查通过；
- 架构、使用与进度文档同步更新。

全部 System 完成后，重新审计组合根和基础 `core` 分类，再将模式版本从“迁移中”提升为“实现基线”。
