## 当前结论

**状态：🔄 进行中（2026-08-05）。** ODC-01 锁定基线、ODC-02 首轮能力映射、`image-codecs`、`qrcode`、`form-pattern`、`rich-text`、`charts`、`table`、`navigation`、`feedback`、`tree-widgets` 九个公开 capability 与 `agent-control` 应用 builder 的正反门禁、`demo-logging` 根二进制正向对照、五种图形公开选择面的启用/禁用对照、D3D11/OpenGL ES 两种 Active registry recipe、`raw-window-handle` 与未使用的 `bytemuck` 直接边清理、`earcut` 基础几何所有权与性能基线，以及 schema v6 的三十七场景 Windows release + Linux check/release 双目标矩阵已建立；`windows-core` 也已收缩到 Windows target，Agent 已生成 Linux GNU release ELF。但 app/ui/draw/data 的整体能力分区、Agent 的真实 Linux 运行时 IPC、D3D12/Vulkan/Metal 的统一薄 RHI/Active registry/目标平台运行、其他 target、全能力和产物符号/资源矩阵仍未完成，尚未满足完整的使用方按需编译契约。使用文档不得在总门禁通过前把本目标描述为已交付能力。

## 已有基础

- `ash`、`glow`、`khronos-egl`、`serde`、`serde_json` 中的一部分已是 optional dependency，并由 backend、`settings-serde` 或 `agent-control` feature 接入。
- Windows、Unix、Wayland 等平台依赖已有 target `cfg` 边界，非目标平台依赖不会无条件进入同一目标构建。
- release profile 已配置 `opt-level = "s"`、`strip = "symbols"`、fat LTO 与单 codegen unit，有利于最终不可达代码裁剪。
- `agent-control`、`settings-serde`、测试门面以及部分 backend 实现已有条件编译。

以上只说明存在基础设施，不等于使用方应用已经做到“只编译所用部分”。

## ODC-01 首批基线入口

首批 fixture 位于 [`fixtures/usage-build`](../../fixtures/usage-build/README.md)，采集脚本为 [`scripts/measure_usage_build.py`](../../scripts/measure_usage_build.py)。从仓库根目录运行：

```powershell
python scripts/measure_usage_build.py --dry-run
python scripts/measure_usage_build.py --locked
```

采集器对每个 fixture 默认执行 `cargo clean`、`cargo metadata`、依赖 package、既有 package 上的精确 Cargo feature 与 `uix` feature 正反断言、正向 build/check 或预期失败 check、`cargo clean`，以保证不同入口之间不复用构建产物，且正常结束后不留下 Rust `target`。schema v6 会从 `rustc -vV` 解析 host target，向 metadata 传入 `--filter-platform <target>`，并让 build/check 显式使用同一个 `--target`，避免把其他目标的条件依赖混入当前 resolved graph；对于没有专属第三方 package 的源码 capability 或只给既有 package 增加 API feature 的 backend，采集器分别读取 `uix` 与目标 package resolve 节点的实际 feature，而不以依赖数量猜测边界。跨宿主 release 必须显式设置 Cargo 标准 target linker 环境变量，采集器在构建前记录实际覆盖并执行 `--version` 探针；缺少或不可执行时直接失败。没有目标 linker 的跨目标入口仍可声明为真实正向 `cargo check`，但这种场景不生成或冒充 release 产物。仅在显式传入 `--keep-build-artifacts` 时保留后置构建产物；运行环境没有 Cargo 或无法确认 rustc host target 时只能使用 `--dry-run`，不会生成虚假的基线证据。

2026-08-04 在提交 `ceceff33b28e352d9120713a2ed6506b911cef7a` 上完成首轮 locked clean-build。环境为 `rustc 1.97.1 (8bab26f4f 2026-07-14)`、`cargo 1.97.1 (c980f4866 2026-06-30)`、默认 host/target `x86_64-pc-windows-gnu`；三个场景均通过 metadata、release build 与后置清理。该轮使用的 schema v1 尚未向 metadata 传入 `--filter-platform`，因此下表的 resolved package 同时包含不同 target 条件分支，只保留为改造前历史计数：

| 场景 | feature 入口 | resolved package | clean release build | release 产物 |
|---|---|---:|---:|---:|
| `minimal` | `default-features = false` | 84 | 98.330 s | 17,808,892 B |
| `d3d11-default` | 改造前默认 `d3d11` | 84 | 111.146 s | 18,149,551 B |
| `settings-serde` | `default-features = false, features = ["settings-serde"]` | 91 | 108.287 s | 17,798,435 B |

其中 build 耗时与 release 产物仍绑定上述工具链、Windows target、feature 集和提交，可用作改造前同机历史对照；resolved package 数未绑定单一 target，不能证明 Windows 依赖边界，也不能与 schema v2 及后续版本的目标过滤计数直接比较。采集 JSON 位于忽略目录 `test-reports/usage-build-baseline.json`，后续 capability 变更必须在对应干净提交上重新生成，不得沿用本表冒充新证据。

## ODC-02 首轮能力映射

首轮事实盘点见[使用方按需编译能力映射](../架构/使用方按需编译能力映射.md)。当前结论是：backend、`settings-serde`、`agent-control`、`image-codecs`、`qrcode`、`form-pattern`、`rich-text`、`charts`、`table`、`navigation`、`feedback`、`tree-widgets` 与 `demo-logging` 已有 feature 边界，Windows 与 Linux 目标的 resolved graph 已按各自 target 条件隔离；唯一 `#[implement]` 宏归属 Windows TSF 路径，因此 `windows-core` 已随其收缩到 Windows target。五个公开 `GraphicsBackend` 变体现在分别随同名 feature 收缩，均已有 Windows release 与禁用 compile-fail 的选择面证据；其中只有 D3D11/OpenGL ES 已接入 Active registry recipe，D3D12/Metal 仍为测试门控，Vulkan registry 固定 Disabled 且现有 context 只有 PixelUpload、没有统一薄 RHI，不能把选择面 release 写成生产 backend。native registry 的常驻诊断条目不再被误写成使用方可选 capability。但 app/ui/draw/data 的整体 capability 仍未独立裁剪。`tracing-subscriber` 已确认只归属演示程序并完成 optionalize，库的基础 `tracing` 事件契约不受影响；`raw-window-handle` 与 `bytemuck` 的无引用直接边均已删除，后者只在启用图片能力时由 `image` 合法传递引入。`ab_glyph` 是 `FontService` 当前无条件构造的唯一文字后端，现阶段属于基础 Typography 契约；`earcut` 只服务基础 Canvas/path 的严格孔洞快速路径，已有本地复杂轮廓分解虽然通过同一正确性契约，但同机热运行中位耗时回退 48.2%、每次输出三角形数从 256 增至 704，因此继续作为基础 Geometry 实现依赖。`image-codecs` 只裁剪第三方压缩格式解码与路径型公开方法，核心 RGBA 位图、裁剪、离屏和预加载句柄绘制仍属于基础契约；`form-pattern` 只裁剪正则规则，基础表单模型和非正则校验仍属于常驻能力；`rich-text` 裁剪组件实现、公开内容模型、解析/布局辅助与内部 patch、快照、文字选择分派，但继续复用基础文字能力；`charts` 裁剪基础与高级图表实现目录、全部公开类型、patch、结构化快照和无障碍摘要，但继续复用基础绘制、主题、文字与交互能力；`table` 裁剪基础表格、泛型数据表、列/分页公开模型、patch、结构化快照、render handler 与动态树刷新，但继续复用基础绘制、主题、文字、交互和虚拟滚动能力；`navigation` 裁剪完整导航组件目录、全部公开类型、patch、结构化快照、无障碍转换与导航兄弟项刷新，但继续复用基础绘制、主题、文字、布局、交互与状态能力；`feedback` 裁剪反馈组件目录、`prelude` 与全局 `message()`/`notify()`、patch、快照、无障碍转换、应用通知覆盖层和 Modal 树钩子，同时把被 `FloatButton`、`Dropdown`、`Slider` 复用的 `TriggerMode`、`TooltipPlacement` 与提示气泡绘制原语保留在基础模块；`tree-widgets` 裁剪 `Tree`、`TreeNode`、`TreeSelect`、`DropPosition`、`SnapshotTreeNode`、兼容重导出、patch、快照与无障碍分派，同时保留通用 `AccessibilityRole::Tree`、虚拟滚动与基础 `tree!` 宏；`agent-control` 已证明公开 builder、JSON 依赖与 Windows/Linux transport 源码可独立启用，关闭后同步消失，并能生成 Linux GNU release ELF；Linux socket 权限、同 UID 校验与端到端 IPC 尚未在目标主机运行。该状态不等于已完成使用方按需编译门禁。

## 实施顺序

1. **基线**：固定工具链、目标平台、clean-build 条件和三个代表性使用方应用，得到未经改造的编译与产物验证。
2. **能力图**：从第三方依赖和大体积组件开始划 capability feature，写明传递依赖与不兼容组合。
3. **编译隔离**：先 optionalize 专属依赖，再对 module 加 `cfg`；同 crate 隔离仍不足时才拆独立 crate。
4. **公开面收缩**：同步门面、`prelude`、示例和未启用能力的编译错误，不保留绕过 feature 的公开路径。
5. **使用方门禁**：执行最小、单能力、backend / target、全能力矩阵，检查依赖图、clean-build 计时与 release 产物。
6. **交付**：门禁通过后再修改使用文档和默认 feature 策略，并记录兼容性影响与迁移方式。

## 完成门禁

只有同时满足以下条件，状态才能改为“✅ 已完成”：

- 至少一个最小 GUI 使用方 fixture 能在关闭默认 feature 后，仅启用明确列出的能力完成 clean release build。
- 未选能力的专属依赖不出现在该 fixture 的 Cargo resolved graph 与构建日志中。
- 每个公开 capability feature 都有独立或声明组合的编译验证；默认、无默认、单 backend 与全能力矩阵通过。
- 至少选取图像/二维码、富文本/正则、Settings serde、Agent 和两个图形 backend 做“启用前后”产物对比，证明专属内容只在启用后出现。
- 使用方最小集与完整集在同条件下记录 clean-build 时间和 release 二进制大小；结论绑定工具链、target、feature 集与 commit。
- 使用文档明确说明 feature 选择、默认集合和迁移方式，不把运行时开关写成编译期裁剪。

## 风险

- Cargo feature 会在整个依赖图中合并；任一传递依赖重新启用能力，都会使其进入构建。
- 过细 feature 会放大组合数量与维护成本，过粗 feature 又无法减少编译成本；粒度必须用基线数据决定。
- 修改默认 feature 或条件导出属于使用方可见兼容性变化，实施时需单独评估版本与迁移策略。
- 二进制变小不能单独证明未用能力没有参与编译；必须同时检查 resolved graph、clean build 和产物。
