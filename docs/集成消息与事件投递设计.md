# 集成消息与事件投递设计

本文承接[System Module Component 设计模式](<System Module Component 设计模式.md>)中被分离出的通信视图，描述异步队列、
跨进程和跨 System 消息。它不描述进程内同步 EventBus，也不能改变 System、
Module、Component 的契约所有权和依赖边界。

## 边界与术语

以下机制必须分开建模：

- `EventDispatcher/EventBus`：进程内同步回调，见[System Module Component 设计模式](<System Module Component 设计模式.md>)；
- `LocalEventQueue`：进程内异步排队，默认不持久；
- `IntegrationBus`：跨 System 发布与消费的逻辑端口；
- `Broker/EventStream`：Kafka、RabbitMQ 等外部传输或持久化日志；
- `EventStore`：以事件追加记录作为领域状态权威。

Message 是跨时间或边界传递信息的总称，Event 只是其中一种。以下类别来自不同维度，
不能当成互斥枚举：

| 分类维度 | 类别 | 语义与处理者 |
|---|---|---|
| 交互角色 | Command | 请求一个明确责任方尝试动作；允许拒绝、失败和结果 |
| 交互角色 | Query | 请求一个明确提供方读取信息；不应隐藏领域副作用 |
| 交互角色 | Reply/Receipt | 与一个请求相关，向指定调用方报告查询结果或已经建立的处理状态 |
| 交互角色 | Signal/Notification | 短寿命通知；可以尽力投递，跨 System 时必须显式命名并接受丢失 |
| 事实语义 | DomainEvent | 已建立的领域事实；零个或多个域内处理者；不可变 |
| 事实语义 | TechnicalEvent | 指标、审计、追踪或基础设施事实；未经提升不得直接驱动领域规则 |
| 事件所有权/范围 | ModuleEvent | Module 拥有并在其私有边界内传播的事件契约 |
| 事件所有权/范围 | SystemEvent | System 拥有并在其内部跨 Module 传播的事件契约 |
| 事件所有权/范围 | IntegrationEvent | 已建立事实的版本化公开投影；面向零个或多个跨 System 逻辑订阅 |

一条消息可以同时命中多个分类，例如 SystemEvent + DomainEvent，或由 TechnicalEvent
投影出的 IntegrationEvent。CrossSystemSignal 是跨边界 Signal，不因经过 Broker
就变成可靠的 IntegrationEvent；它可以携带可丢失的提示或采样，但不建立“接收方
必须观察该事实”的公开义务。一旦消息被定义为 IntegrationEvent，就适用事实与
R1/R2 规则，不能再用 Signal 名称降低保证。
Reply/Receipt 不是广播 Event，也不创造它所报告的业务结果；需要让多个独立消费者
观察 Command 完成事实时，应从已经建立的提供方状态另行投影 IntegrationEvent。

需要立即结果、固定顺序、全部成功或总体补偿时，使用直接契约、Workflow、Saga 或
Process Manager，不能用广播消息掩盖责任方。

## 事实、生产与消费状态

领域事实建立、生产方投递和订阅方处理是独立状态线：

```text
事实状态：PendingEventRecord → FactEstablished / Discarded
事件提升：FactEstablished → 可选 DomainEvent / TechnicalEvent → 可选 IntegrationEvent 投影
每条生产路由：Prepared → Submitted（可选 Enqueued）
                         ├→ DestinationAccepted
                         ├→ NotDelivered / DeliveryUnknown → Retry → 回到 Submitted
                         └→ Expired / Blocked
每个逻辑订阅：Received → Processing → Processed / Retry / DeadLettered
调用方 Command 意图：IntentCreated（生产边界原子提交后建立）
提供方 Command：Received
                 ├→ Accepted → Completed / Failed / Cancelled
                 │    └→ CancellationRequested → Cancelled / TooLate
                 ├→ Rejected
                 └→ ExpiredBeforeAcceptance
调用方 Command 观察：LastKnownState ─响应不确定→ OutcomeUnknown ─回执/查询→ ReconciledState
跨 System Query：RequestCreated → Responded / NotDelivered / Expired / ProviderFailed
```

这些是必须区分的语义状态，不要求实现采用相同名称或数量。R1/R2 路由进入 Blocked
时仍保留记录、告警和恢复所有权，不能把“当前无法投递”实现成静默丢弃。
`ExpiredBeforeAcceptance` 与 Rejected 一样是提供方的权威结论：原请求未被接受且
不会稍后执行；它不同于调用方等待超时。两者按拒绝原因区分：Rejected 表示提供方
基于业务、策略或校验拒绝该意图；ExpiredBeforeAcceptance 表示意图未在截止时间内
被接受、接受窗口已过。两种结论都不得在稍后按同一意图执行。

`FactEstablished` 是语言和存储无关的事实建立点：从该点起，事实所有者把命题视为
成立，后续局部失败不能把它改写为“从未发生”。它可以由事务提交、Event Store
成功追加、原子状态转换、权威外部确认或其他等价机制实现。

`PendingEventRecord` 是事实建立前的候选记录或事务内通知，不是已经成立、可跨边界
观察的 DomainEvent。只有越过 FactEstablished 后才能提升为 DomainEvent，或进一步
映射为 IntegrationEvent；建立失败或已经放弃建立的候选必须进入 Discarded。采用
事务时，回滚必须丢弃候选；建立前处理器只能修改同一工作单元覆盖的状态或原子追加
Outbox，不能执行不可回滚的外部副作用。

D1 若要求多个参与者全部成功或共同回滚，应使用显式事务调用链或 Pipeline；它不是
SMC 进程内 EventBus 的事实广播，不能依赖无序观察者扇出来形成原子业务步骤。

`DestinationAccepted` 只表示目标传输端点、队列或 Broker 已按本路由确认接管；R1
路由还必须到达声明的持久确认点。它不表示任何订阅方已经处理，也不表示 Command
已被业务接受或完成。只有传输层能够证明请求未被目标接收时，才可标记
`NotDelivered`；连接中断、超时或响应丢失无法证明这一点时应标记 `DeliveryUnknown`。
不得用一个全局 `Published`、`Accepted` 或 `Consumed` 状态概括所有路由、请求和订阅。
实现可以在一次响应中合并多个阶段，但契约和观测仍必须区分传输接管、业务接受和
业务完成。`OutcomeUnknown` 是调用方对真实业务状态暂不可知的观察，不是提供方的
业务终态；响应丢失或超时时不能推断为 Rejected、Failed 或“已经取消”。
Reply/Receipt 只能在对应查询结果或 Command 状态已经由提供方建立后产生；响应投递
失败不撤销该结果，调用方按回执重试或状态查询契约恢复观察。

## 投递边界与保留配置

“何时、跨什么边界投递”和“记录保留多久、能否重放”是两个正交维度。

投递边界：

| 配置 | 适用范围 | 语义边界与失败语义 |
|---|---|---|
| D1 本地事务内 | PendingEventRecord / 事务内通知 | 提交前同步处理；只修改同一工作单元或原子追加 Outbox，回滚时一并丢弃 |
| D2 本地建立后 | System 内 FactEstablished 后的通知 | 失败不能伪装成领域回滚；声明可丢或可恢复 |
| D3 跨 System | IntegrationEvent、公开 Command/Query/Reply/Receipt 或显式 CrossSystemSignal | Event 遵守 FactEstablished；请求与响应遵守各自契约；Signal 可以尽力发送，但不得承载接收方必须获知的事实 |

记录与保留：

| 配置 | 权威性与保留语义 | 最低保证 |
|---|---|---|
| R0 瞬时 | 没有独立持久记录，不承诺崩溃恢复；单向消息可能丢失，请求路径必须显式返回可证明的未送达、超时或未知结果 | 明确容量、过载、Signal 的可接受丢失、Command/Query 的失败与超时，或结果通知的权威查询恢复 |
| R1 可恢复投递记录 | 以 Outbox、持久队列或等价记录保存到本路由确认点、过期或合规处置；不承诺任意历史重放 | durability、确认点、重试、死信和保留期 |
| R2 派生可重放流 | 已建立事实的可恢复派生日志，不是领域事实权威 | 分区顺序、checkpoint、schema 演进和重放控制 |
| R3 权威 Event Store | 成功追加本身建立领域事实 | 并发版本、原子追加、历史升级、快照和完整重建 |

允许组合按消息语义选择：

- D1 通常使用 R0；D2 可以使用 R0/R1/R2；
- D3 CrossSystemSignal 只在允许丢失时使用 R0；
- D3 IntegrationEvent 必须使用 R1/R2；
- D3 Command 的有界同步请求可以使用 R0，但调用方必须得到明确的未送达、超时或
  DeliveryUnknown；后两者可能表示 OutcomeUnknown，重试必须复用稳定 command id；
  异步或不得丢失的 Command 使用 R1，并以同一身份保证幂等；不得用 R2 普通重放
  重新执行历史意图；
- D3 Query 通常使用 R0 请求/响应；异步 Query 可以使用 R1，但必须声明一致性、
  correlation、结果保留期和过期语义，不使用 R2 重放历史读取。
- D3 Reply/Receipt 在同步请求路径中随 R0 响应返回；异步结果通常使用 R1。只有结果
  已由权威状态保存且调用方能确定性查询恢复时，才可把即时通知降为 R0 Signal；普通
  Reply/Receipt 不使用 R2 重放来重新回答历史请求。

R3 是领域持久化配置，向外投影时仍要另选 D2/D3 和 R1/R2，不能把 Event Store
当作投递目的地配置。
D1 处理器在同一事务追加 Outbox 时，D1 记录本身仍是 R0；该 Outbox 是原子创建的
另一条 `D3 + R1` 生产路由，必须分别记录两条路由的状态和保证。
这一步只准备生产意图；Relay 只能在所属原子边界提交后读取 Outbox。事实消息的该
边界同时成为 FactEstablished；Command 的该边界只建立 IntentCreated，不代表提供方
已经 Accepted 或 Completed。

## SMC 边界映射

`ModuleEvent`、`SystemEvent`、`IntegrationEvent` 属于契约所有权与传播范围分类；
`DomainEvent`、`TechnicalEvent` 属于事实语义分类。两个维度正交：ModuleEvent 或
SystemEvent 只要表达 FactEstablished 后的领域事实，就可以同时是 DomainEvent；
跨 System 时则重新投影为公开 IntegrationEvent。它们不因名称不同而形成强制的
逐层转换关系。

```text
所有权 / 范围轴：
ComponentOutput
├─ 固定接收者 → 返回值或窄回调
└─ 可选提升 → ModuleEvent
              └─ 确有跨 Module 价值时再映射 → SystemEvent

语义 / 发布轴：
边界拥有的候选记录
→ FactEstablished
→ 值得通知时按语义分类为 DomainEvent 或 TechnicalEvent
└─ 确有跨 System 价值时可选投影 → IntegrationEvent
   → IntegrationBus 端口
   → Broker Adapter → Broker / EventStream
   → 消费 Adapter → 消费 System 的公开消息入口
                → 显式处理器 / Workflow / 可选内部意图或事件

跨 System 请求轴：
调用 System → 提供方公开 Command / Query 契约
→ D3 请求 Adapter → 提供 System
→ 显式 NotDelivered / Accepted / Rejected / Result / Timeout / OutcomeUnknown 契约

短寿命状态或技术提示
→ 显式 CrossSystemSignal → D3 + R0 Adapter → 尽力发送，允许未送达
```

普通 Component 不得构造 IntegrationEvent。跨边界提升必须由当前边界重新拥有
类型、失败和版本语义，并移除私有对象布局、事务对象、内部错误和实现句柄。
Command/Query 是意图或读取请求，不得伪装成 IntegrationEvent，也不要求
FactEstablished；它们必须由请求方和提供方公开契约明确责任方、结果和有效期。
消费 Adapter 只负责验证、反序列化、版本转换和调用公开消息入口，不决定业务响应。
若消费 System 因外部 Event 需要发起内部 Command，必须由自己的边界显式创建并拥有
该意图、幂等和失败语义，不能把外部事实机械改名为 Command。

IntegrationBus 默认是端口，Broker 客户端是 Adapter，外部 Broker 是外部资源。
只有产品真正拥有消息服务的路由治理、多租户、SLO、运维和完整生命周期时，才把
它建模为 Messaging/Integration System。

## 公开消息契约

IntegrationEvent 是 FactEstablished 后事实的稳定公开投影，不是内部对象序列化
结果。负载必须不可变，不携带发布方对象引用、回调、事务上下文、密码、访问令牌、
会话对象或可转移授权能力。

公开 Command/Query/Reply/Receipt 同样必须使用不可变、版本化契约。Command 至少声明稳定
command id 及其命名空间、请求方、目标责任方、请求语义指纹、幂等与结果保留窗口、
截止时间的时间基准、判定方、时钟偏差容忍和含义、Accepted/Rejected、
Completed/Failed/Cancelled 和结果契约；Query 至少声明 request id、提供方、一致性、
截止时间的时间基准与判定方、correlation、响应、错误、结果保留和过期语义。
Reply/Receipt 至少声明关联请求身份、提供方、已经建立的状态或结果、产生时间、保留
和恢复方式；报告演进中状态时还要携带由提供方定义、在同一关联请求内单调的
revision/sequence，防止
乱序响应使调用方状态倒退。公共信封字段可以复用，但不能抹掉消息角色差异。

IntegrationEvent 可采用 CloudEvents 信息模型统一信封，至少治理：

- 稳定 `type`、`source` 和在 source 内唯一的 `id`；
- `subject`、发生时间、内容类型和 schema 引用；
- correlation、causation 与 trace context；
- 公开业务负载、分区键和最小必要租户声明；
- 数据分类、加密、保留、删除和重放权限。

业务负载中的 producer、tenant、user、role 等声明不能自行赋予权限。身份必须来自
本路由认可且可验证的认证上下文，授权必须同时约束生产方、消费方、operation、租户
和重放主体；command id、event id 与幂等键只解决消息关联和重复识别，不是防伪或
防重放凭证。

CloudEvents `specversion`、事件 type/schema 版本、业务 sequence 和 Broker
partition/offset 是不同概念。字段删除、重命名、单位变化、枚举收窄和语义改变
按不兼容变更处理；未知字段、未知枚举、新旧版本并行和消费者升级窗口必须明确。

异步消息路由可以用 AsyncAPI 记录 channel、operation、message schema、correlation
ID 和 Broker binding；同步或请求/响应路由使用与传输匹配的 API 契约描述。SMC 仍
负责记录契约所有者、订阅理由、业务结果和恢复责任。路由清单与所采用的描述通过
稳定标识互相引用，不能各自维护一份会漂移的路由事实。
异步 Command/Query 的响应、完成通知、处理收据或状态查询不是“隐含返回值”，而是
独立公开契约与路由；它们必须分别声明 D/R、correlation、确认点、保留、访问授权和
调用方离线时的恢复方式。

## 一致性与可靠投递

IntegrationEvent 不得早于 FactEstablished。事实建立可以由事务提交、Event Store
追加、原子状态转换或权威外部确认实现；需要 `D3 + R1/R2` 时，已建立事实或对应的
生产意图还必须能够持久恢复或从权威来源重新推导。领域状态与外部 Broker 不能
原子写入时，发布方使用 Transactional Outbox、CDC 或可靠事件日志。事务型路径为：

1. 在领域事务内把待发布记录与领域状态一起提交；
2. Relay 只读取已经提交的记录；
3. 目的地持久确认后更新生产状态；
4. 接受 Relay 重试导致的重复投递。

跨 System Command 的生产记录只证明“请求意图已建立”，不证明业务动作已经接受或
完成。传输确认、业务 Accepted/Rejected 和 Completed/Failed/Cancelled 必须分别建模；重试
使用稳定 command id、幂等处理和截止时间。同一 id 的重试必须与首次请求的语义指纹
一致，不一致时拒绝为身份冲突；指纹覆盖契约版本、目标责任和不可变业务参数，不把
trace、重试次数或可更新认证材料误当成新意图。去重状态和既有结果保留窗口至少覆盖
声明的消息存活、重试和结果核对期限；窗口过后如何拒绝或重新发起必须成为契约。
Query 必须声明读取一致性、请求截止时间、correlation、响应或错误契约，并保持无
隐藏领域副作用。
传输超时、连接中断或响应丢失可能发生在命令已经执行之后，此时结果是
OutcomeUnknown，而不是 Rejected。Rejected 必须保证该请求未被接受且不会在稍后按
同一意图执行；Failed 表示已接受后的业务失败。截止时间或调用方超时只限制请求准入、
调用方等待或协作取消中的哪一项，必须明确声明，不能自动当成提供方已经停止执行。
调用方只能在去重窗口内使用同一 command id 重试，或通过状态查询、处理收据等显式
协议消除不确定性。
如果协议支持取消，`CancellationRequested` 只是另一项请求或状态转换，不等于
`Cancelled`。取消请求有自己的 Cancelled/TooLate 等结果；`TooLate` 表示取消未改变
原 Command，它仍会或已经解析为 Completed/Failed。提供方必须为竞争规定确定性优先级，
使原 Command 最终只处于 Completed、Failed 或 Cancelled 之一。传输断开本身不得
充当取消请求。

Outbox 解决发布方双写，不提供端到端恰好一次。R1/R2 路由中会产生可变业务效果的
消费者使用 Inbox 或等价幂等状态；存在共同原子边界时，把去重记录、消费者领域状态
和后续 Outbox 一起建立，Broker ack/offset 在本地结果提交或持久转交后确认。无法
纳入同一边界的支付、邮件或第三方调用必须使用稳定幂等键、调用收据或补偿流程。

`D3 + R0` 只适用于允许丢失的显式 CrossSystemSignal（包括可从权威状态恢复的结果
提示），或有明确未送达与超时语义的有界 Command/Query；Command 还必须处理
OutcomeUnknown。Signal 不进入 Outbox、不
承诺重试，接收方不得依赖它建立不可恢复的领域状态；只要“漏掉一次”会改变业务
正确性，该事实消息就必须提升为 IntegrationEvent，并采用 R1/R2。Command/Query
是否安全则由调用方能否处理失败、重复、超时和未知结果判定，不能用“尽力而为”
静默丢弃请求。

每条路由必须明确：

- 至多一次或至少一次，以及允许丢失和重复的范围；
- 顺序保证限定到哪个聚合、键、分区或逻辑订阅；
- 瞬时错误、永久业务拒绝和毒消息的重试分类；
- 容量、背压、过载降级和溢出策略；
- 死信的负责人、告警、修复、重放或合规丢弃流程；
- live/replay 上下文以及不可重放副作用的隔离策略。

## 路由与逻辑订阅

逻辑订阅是承担一项事件响应结果的稳定身份。一个 IntegrationEvent 为每个逻辑订阅
建立一项独立处理义务，物理投递可以重复；同一逻辑订阅下的多个运行实例只做负载
均衡和故障接管，不代表多个业务订阅。Command 必须有且只有一个逻辑处理责任方，
Query 必须有且只有一个明确提供方；重复、缺失或歧义路由应在启用前失败。
Reply/Receipt 必须关联一个逻辑目标调用方；需要广播结果时另行投影 IntegrationEvent。
CrossSystemSignal 的接收方不得成为业务正确性的必要条件。

每条跨 System 路由至少记录通用字段：

- 消息类型、schema 版本、契约所有者、交互角色、所有权/范围、语义和发布边界；
- 逻辑订阅、Command 责任方、Query 提供方或 Reply/Receipt 目标调用方，以及对应
  Adapter 身份；
- D/R 配置、传输绑定和稳定路由标识；
- 适用的顺序键、重复、去重窗口、重试、背压、失败恢复和重放策略；不适用项必须
  显式声明；
- 数据分类、租户范围、认证来源、授权决策方与策略、完整性与机密性、保留期、重放
  权限和负责人；
- 启用条件、SLO、兼容范围和废弃计划。

还必须按消息语义记录条件字段：

- 事实消息记录 FactEstablished 的实现与证据，以及生产意图的持久恢复或重新推导；
- 发布/订阅路由记录 topic、queue、subscription、consumer group 或等价消费身份；
- Command 记录 intent owner、目标责任方、command id 命名空间、语义指纹、幂等与
  结果保留窗口、截止时间基准/判定方/偏差容忍及取消语义、endpoint/operation、
  Accepted/Rejected、
  原 Command 的 Completed/Failed/Cancelled、CancellationRequested/TooLate、
  OutcomeUnknown，以及
  回执、结果或状态查询路由；
- Query 记录提供方、endpoint/operation、一致性、correlation、截止时间基准与判定方、
  响应、错误与过期语义；异步 Query 还记录响应路由、结果保留期和调用方恢复方式；
- Reply/Receipt 记录关联请求身份、结果建立证据、目标调用方、correlation、D/R、
  结果保留与查询恢复方式；演进中状态还记录 revision/sequence 与乱序处理；
- CrossSystemSignal 记录允许丢失的依据、影响范围和降级方式。

自动扫描、注解注册或动态发现只有在能生成并检查等价路由清单时才可采用。发布者
不知道消费者实现，不表示契约依赖消失；反馈回路必须由 Workflow/Saga 或中立
协议管理 correlation、幂等、最大迭代和终止条件。

## 生命周期、可观测性与测试

业务 System 只管理自己的 Adapter、连接租约、Relay、Inbox、消费身份和订阅；
外部 Broker 生命周期属于平台或提供方。关闭契约必须声明停止接收新工作的线性化点、
drain deadline、在途消息的当前所有者和超时策略：

- R0 可以按已经声明的丢失策略放弃在途 CrossSystemSignal；
- R0 Command/Query 停止接收新请求后，在途请求必须完成，或向调用方报告可证明的
  NotDelivered 或超时；Command 结果不确定时还要报告 OutcomeUnknown。不得把关闭
  伪装成 Rejected、Failed 或取消成功；
- R1/R2 只能完成处理、持久转交，或保持未确认状态以便恢复和重新投递；
- Broker 输入必须在本地处理结果提交或持久转交后才确认；
- stream checkpoint 必须与派生状态原子提交，或在持久转交恢复所有权后推进；
- Outbox 必须保留到目的地持久确认接管，或另一恢复主体持久接管生产责任；
- 任何路径都不得在仍是唯一恢复所有者时释放对应记录、租约或客户端；
- 超过 drain deadline 不会降低原投递保证，必须报告阻塞路由，并按原配置保留恢复
  责任，再释放不再拥有在途工作的订阅和客户端。

可观测性应区分生产、发送、接收、处理和确认，并保留 correlation、causation 和
trace 关系。指标至少覆盖每个低基数消息类型与处理身份的发布、成功、失败、延迟、
积压、重试、死信和重放；Command 还应区分传输接管、业务接受、业务完成、取消请求、
取消结果与 OutcomeUnknown。日志、trace 和指标默认不得记录敏感负载。

验证至少覆盖：

- schema 兼容、未知字段和新旧版本并行；
- 事务提交、Event Store 追加、原子状态转换等 FactEstablished 实现具有等价提升
  语义，建立失败或回滚不会泄漏 PendingEventRecord；
- 所有权/范围分类与语义分类分别验证，ComponentOutput、ModuleEvent、SystemEvent
  不会被强制逐层提升，TechnicalEvent 也能按需投影为可靠 IntegrationEvent；
- 消费 Adapter 不机械把 IntegrationEvent 改名为 Command；确需内部意图时，由消费
  System 创建新的责任、身份、幂等和失败语义；
- D3 Command 区分传输确认、业务接受和业务完成，重复与超时不会执行额外业务动作；
- Command 响应丢失产生 OutcomeUnknown，使用同一 command id 重试或状态查询不会
  重复业务效果；
- 只有传输层能证明目标未收到时才产生 NotDelivered；Rejected 后同一意图不会延迟
  执行，调用方超时也不会被误当成取消成功；
- 延迟、积压和时钟偏差下，截止时间由契约指定的一方按同一时间基准判定；已经
  ExpiredBeforeAcceptance 的请求不会稍后执行；
- CancellationRequested 与 Cancelled 分别验证；取消和完成竞争只产生契约允许的
  原 Command 唯一终态，TooLate 后仍能取得原 Command 的 Completed/Failed 结果，
  传输断开不会隐式取消业务动作；
- 相同 command id 与不同语义指纹产生身份冲突；去重/结果窗口内可重复取得同一结果，
  窗口过后按契约拒绝或显式创建新意图；
- 异步 Command/Query 的响应、回执和状态查询路由独立验证 D/R、correlation、保留、
  授权和调用方离线恢复；
- Reply/Receipt 不早于所报告结果或状态的建立点；投递失败不会回滚结果，也不会被
  重复消费解释成新的 Command/Query；
- 重复或乱序 Reply/Receipt 不会让调用方从 Completed/Failed/Cancelled 等终态倒退到
  Accepted 或其他较早阶段；
- D3 Query 验证一致性、correlation、超时、响应错误和无隐藏领域副作用；
- 伪造的 producer、tenant、user 或 role 负载字段不能越过认证与授权边界；未授权生产、
  消费和重放均被拒绝且可审计；
- 路由清单与所采用的 API/消息描述保持稳定标识、方向、operation 和 binding 一致；
- 路由清单只对事实消息要求 FactEstablished，Command、Query 和 Signal 使用各自的
  条件字段；
- `D3 + R0` 验证丢失、断线和过载时不会破坏业务正确性；
- R0 结果提示丢失后，调用方能从已声明的权威查询读取相同或更新状态；
- R1 分别以 Outbox、持久队列或等价投递记录验证确认点、恢复和过期语义；
- Outbox Relay、目的地确认、Inbox 原子性、重复、乱序和缺口；
- 关闭 R1/R2 路由时，未完成消息保持未确认或持久转交，不因 drain 超时丢失；
- 消费实例扩缩容、重试、死信、背压、关闭和崩溃恢复；
- 历史 schema、checkpoint、重放副作用、保留和恢复边界；
- 使用真实 Broker 的序列化、确认、重平衡和实际投递保证。

## 集成消息硬不变量

- **IM-01 分类正交**：Command、Query、Reply/Receipt、Signal 是交互角色；DomainEvent、
  TechnicalEvent 是事实语义；ModuleEvent、SystemEvent、IntegrationEvent 是事件
  所有权/范围。一个消息可以同时命中不同维度，但不能混淆各维度的保证；
- **IM-02 事实先于事实消息**：DomainEvent、TechnicalEvent 和 IntegrationEvent
  只能表达 FactEstablished 后的事实；PendingEventRecord 不可跨该边界观察。
  Command/Query 不是事实，遵守各自的请求、结果和有效期契约；Reply/Receipt 只能
  报告提供方已经建立的结果或状态，不能通过发送响应创造该结果；
- **IM-03 D/R 正交**：投递边界 D 与记录保留 R 分别选择；任何 D 配置都不能隐含
  持久化、重放或权威性，任何 R 配置也不能改变契约所有者和业务责任方；
- **IM-04 接管不等于业务完成**：DestinationAccepted、Command Accepted、Command
  Completed/Failed/Cancelled 和订阅 Processed 是不同状态，必须分别记录和观测；
  NotDelivered 只在能证明目标未收到时成立，Rejected 保证同一意图不会稍后执行；
  OutcomeUnknown 是调用方观察而非业务终态，不能被解释为 Rejected、Failed 或取消成功；
- **IM-05 投递配置匹配语义**：IntegrationEvent 使用 R1/R2；CrossSystemSignal 只有
  在允许丢失时使用 R0；Command 仅在有明确未送达、超时和 OutcomeUnknown 语义的
  有界请求中使用 R0，异步或不得丢失时使用 R1；Query 使用 R0 或有明确过期语义的
  R1；异步 Reply/Receipt 使用 R1，或仅在结果可从权威状态确定恢复时退化为 R0 Signal；
  Command/Query/Reply/Receipt 不使用 R2 重放历史交互，也不能冒充 Event；
  CrossSystemSignal 的接收方不得成为业务正确性的必要条件，更名或经过 Broker
  不能把它提升为 IntegrationEvent 的保证；
- **IM-06 可靠不等于恰好一次**：R1/R2 必须接受重复、重试和恢复；消费者、Command
  处理者及外部副作用通过稳定身份、语义指纹、足够的去重窗口、幂等状态、调用收据
  或补偿保证业务效果；
- **IM-07 责任转移先于确认**：需要原子关联的生产意图与领域状态在同一边界或等价
  恢复协议中建立；消费者在本地结果提交或持久转交后才确认 Broker 输入或推进
  checkpoint；Outbox 在目的地或另一恢复主体持久接管前不得释放；
- **IM-08 状态按路由和处理身份隔离**：生产状态按路由记录，消费状态按逻辑订阅、
  Command 责任方、Query 提供方或 Reply/Receipt 目标调用方记录；不得用全局
  Published、Accepted 或 Consumed 掩盖部分成功；
- **IM-09 关闭不降低保证**：R1/R2 关闭和 drain 超时只能完成、持久转交或保持未确认，
  不能丢失唯一恢复所有权；R0 只有 Signal 可按已经批准的丢失策略放弃，Command/Query
  必须返回结果、可证明的未送达、超时或适用的 OutcomeUnknown；
- **IM-10 公开契约稳定且最小**：跨 System 消息使用版本化公开契约，不泄漏私有对象、
  事务上下文、实现错误、凭据或可转移授权；负载声明不能自行赋权，认证、授权、数据
  分类、租户、完整性、机密性、保留、重放和废弃责任必须可查；
- **IM-11 重放不伪装实时处理**：live 与 replay 上下文必须可区分；不可重放副作用
  使用隔离、幂等、收据或补偿，历史重放不得静默重复外部业务动作；
- **IM-12 身份重用保持同义**：同一 command id 只能表示同一语义指纹；在已声明去重
  和结果窗口内重试必须复用该 id，窗口过后不得静默当作新意图执行；
- **IM-13 时间限制不冒充取消**：截止时间和调用方超时必须声明判定方及其控制的是
  准入、等待还是协作取消，并声明时间基准与时钟偏差容忍；未确认提供方停止执行前，
  调用方对尚未得到确定结论的阶段只能视为 OutcomeUnknown，并保留已经确认的最后状态；
- **IM-14 请求取消不等于已经取消**：已接受的 CancellationRequested 必须在权威状态
  中解析为 Cancelled、TooLate 或其他版本化结果；TooLate 不替代原 Command 的结果，
  原 Command 在竞争后只处于 Completed、Failed 或 Cancelled 中的一个终态。调用方
  未观察到确认时仍是 OutcomeUnknown，传输断开不得隐式取消业务动作；
- **IM-15 回执不使状态倒退**：报告演进中状态的 Reply/Receipt 使用提供方定义、在
  同一关联请求内单调的 revision/sequence；重复、乱序或延迟响应不得覆盖更新状态，
  也不得让终态回到非终态。
