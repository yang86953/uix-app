# 边界成本度量

[← 返回 UIX Lang 索引](../README.md)

> **文档角色**：实证校准——用真实语料量化"UI 描述留在 `.uix`、业务留在 Rust"这一边界的实际成本，检验[语言边界](语言边界.md)的画点是否成立。
>
> **状态声明**：基线数据采集于 2026-08-27；脚本与重跑方式见文末。数字随代码演进变化，引用时注明采集日期。

## 1. 为什么度量

语言边界的核心争议是"回调管线税"：如果界面轻逻辑被边界切成大量一两行的 Rust 小函数加回调 prop 样板，说明边界画得偏紧；反之如果业务逻辑渗透进 `.uix`，说明偏松。本报告以可重复脚本给出当前仓库的实测分布。

## 2. 方法论

`scripts/measure_uix_boundary.py` 以启发式正则扫描 `src/ui/widgets` 与 `demo/uix-lang-demo/src` 下全部 `.uix` 文件：

| 指标 | 判定规则 |
|---|---|
| 纯界面处理器 | 处理器内调用的驼峰名全部属于 `setState` / `setStyle` / `setTheme` 或本文档声明的 action |
| 回调转发处理器 | 处理器中调用了一个或多个非内置驼峰名（Rust 函数、external 符号） |
| 混合处理器 | 同时包含局部更新与回调转发 |
| 回调 prop | 已声明 `<Widget>` 的回调类型 prop（`(…)` 形状）在调用位以 `{ident}` 传值的次数 |
| external 符号 | `external="…"` 登记的不同符号数 |

PascalCase 调用名视为数据构造器，不计入任何一侧。

## 3. 基线数据（2026-08-27）

```text
文件 96 个 / 共 6287 行
处理器：纯界面 43 | 混合 0 | 回调转发 3
回调 prop 传值：0 次
external 唯一符号：1 个（submit_profile）
```

### 分层观察

| 层 | 组成 | 特征 |
|---|---|---|
| 框架组件库（src/ui/widgets，约 70 文件） | Modal、Form、Table 等 widget 的外观与静态结构 | **事件属性出现 0 次**；交互语义完全由 Rust 内核拥有，`.uix` 只承载结构、样式、Visual 静态值 |
| 应用演示页（demo/uix-lang-demo，4 页 + 外壳） | main 17 处、start 12 处、extended 12 处、core 2 处纯界面处理器 | 全部为 setState/action/setStyle 级别的界面编排 |
| 图形恢复演示 | graphics_recovery.uix 3 处转发 | 有意为之的"驱动类"桥接：注入设备丢失等测试钩子本来就必须由 Rust 实现 |

## 4. 结论

1. **回调管线税 ≈ 0**。全仓没有出现"一个界面开关对应一个 Rust 微函数"的模式：43 处处理器全部在界面侧闭环，跨边界转发仅 3 处且都是业务/平台能力（故障注入钩子、表单提交），本来就是 Rust 的职责。
2. **分层符合设计**。组件库层的零事件属性证明"视觉归 .uix、行为归内核"在最大体量的语料上自然成立；应用层处理器集中在局部状态编排。
3. **混合处理器为 0** 说明现有语料没有同时触碰两侧的胶水场景；若未来该数字增长，应优先审视是否出现了应该下沉到 action 或上提到 Rust 的模糊逻辑。
4. 结论支持维持现行五条准入判定规则，暂无放宽或收紧的语言面调整依据。

## 5. 附加发现

- 扫描过程确认了块级成员语法落地前的真实痛点：extended.uix 单行 `state="…"` 属性长达十余项（含 record 与语义类型初始值）。此类文件迁移到 `@state { … }` 多行形式后可读性显著提升，建议作为新写法的示范样板维护。
- 未启用块的启发性统计无法区分"action 内联展开的转发"与"事件直连转发"；二者编译产物等价，不影响总量结论。

## 6. 局限与重跑

- 启发式基于正则而非完整语法树：多行字符串形式 `props="…"` 与嵌套括号理论上可能漏计；新增语法表面时同步扩充脚本。
- 回调 prop 统计依赖 Widget 声明可见于同一文件；跨文档导入的自定义组件回调不计入（当前语料未出现）。
- 重跑命令：`python3 scripts/measure_uix_boundary.py --markdown`（根目录执行，JSON 模式去掉 `--markdown`）。
