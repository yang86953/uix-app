# UIX 应用模块与动态执行（补充方案）

[← 返回 UIX Lang 索引](../README.md)

> **状态**：补充方案，只记录设计，暂不实现、不进入当前实施排期。Scheme R7RS-small 仍是正在推进的主方案，其 [P0 引擎取证与第一版合同](../../架构/app/extensions-engine.md)继续有效。本文不要求修改当前代码、依赖或验收条件，也不表示新语法和运行 API 已可用。
>
> **文档范围**：UIX 语言扩展的候选范围、类型与效果、AOT / 动态执行一致性、工具链与兼容原则。当前语言边界及可用规则仍由[语言边界](语言边界.md)和[规范](../规范/总览.md)持有；Scheme 主方案的宿主合同与阶段验收继续由[扩展运行时](../../架构/app/extensions.md)和[实施计划](../../架构/动态扩展实施计划.md)持有。本文中的“第一版”和门禁仅适用于补充方案将来单独获准实施的情形。

## 1. 方向与边界

本补充方案探索扩展 UIX 自身的语言能力，使使用方能用 UIX 同时描述界面和应用模块，无需为这些模块另写一种扩展语言。Rust 保留宿主平台能力、性能敏感算法、进程与原生资源生命周期；UIX 应用模块可承担扩展自己的算法、业务规则、状态和异步流程。

Scheme 主方案继续独立实施和验收，保留标准语言、引擎选型、宿主库及动态 UI 描述方式。本文探索运行期解析 `.uix` 和 UIX 业务逻辑两个增量，不替换 Scheme，也不要求现有 `.scm` 扩展迁移；主方案当前不解释 `.uix` 的边界仍然有效。

目标是同一份 UIX 模块可以静态编译进应用，也可以在运行中装载；动态装载不要求重编译宿主。新增算法由模块函数实现，不能把扩展退化成只能从宿主预设动作中选项的配置表。

## 2. 两类模块

| 模块 | 负责 | 不取得 |
|---|---|---|
| 界面模块 | Widget、样式、布局、展示派生、输入草稿、事件绑定 | 宿主领域真值、进程生命周期、任意原生资源 |
| 应用模块（新增目标） | 有类型的数据与函数、命令、业务状态、事件处理、异步流程与导出契约 | 任意 Rust 作用域、私有对象、raw handle、无授权 I/O |

两类模块共用 UIX 的名称、类型、导入、诊断和工具链。界面通过应用模块公开的状态投影与动作交互，应用模块可以没有界面；不要求把业务代码嵌进 Widget 事件属性。文件组织与模块声明语法在补充方案的语义评估阶段确定，不提前发明第二种文件后缀或把伪语法写成可复制示例。

## 3. 应用模块的候选语言能力

| 能力 | 第一版目标 | 实施前必须写清的语义 |
|---|---|---|
| 类型化数据 | 布尔、固定宽度整数、浮点、字符串、字节、数组、record 与显式可选值 / 结果值 | 类型与字面量推导、字段可见性、数值范围、转换、相等性 |
| 函数 | 显式参数和返回类型、局部变量、函数调用与返回、条件分支 | 词法作用域、遮蔽、参数传递、求值顺序、失败出口 |
| 集合计算 | 有界遍历、已有 map / filter 等操作的应用模块使用 | 迭代顺序、是否分配、修改可见性、越界与空集合行为 |
| 模块状态 | 每实例独立的类型化可变状态和只读投影 | 单写者、原子更新单位、revision、导出 / 迁移 schema |
| 动作与命令 | 可带参数的动作、类型化命令与服务实现 | 输入输出、状态修改、宿主效果、取消与重复调用 |
| 异步流程 | 等待宿主任务、接收结果、显式处理失败与取消 | 挂起和恢复、状态版本、超时与关闭、在途资源归属 |
| 模块组合 | 显式 import / export、包内依赖与宿主端口绑定 | 来源闭包、可见性、类型身份、冲突、循环与版本兼容 |

不以实现完整 Rust 为目标。首期不引入任意指针、借用生命周期语法、unsafe、原生 FFI、用户宏系统、任意 `eval`、无限制递归或用户线程。受限闭包沿用既有可验证用途；若开放一般闭包、递归或泛型，必须另补类型、执行与资源契约，不能作为隐式需求混入第一版。

### 状态与效果

纯函数和 computed 只读取输入并产生值，不能写模块状态、发起任务或访问平台。动作可以修改自己实例的状态；带副作用的宿主调用只从显式动作入口发生。加载、初始化候选、视图构建与状态迁移阶段不执行外部写操作。

每实例的同步动作按接受次序串行执行。第一版以 action 的同步片段为状态提交单位：失败前尚未提交的状态变更丢弃；跨 `await` 不保持内存事务或借用。挂起前提交已完成的同步片段，恢复时重新校验实例代、取消状态和被依赖的 state revision，不能持有可变状态锁等待 I/O。恢复冲突显式返回，由动作处理；不自动重跑已产生副作用的片段。

前端登记函数和宿主端口的效果类别，禁止 computed 间接调用写操作。宿主外部效果有独立操作 ID 与完成合同：状态片段回滚不撤销已经发生的文件写入或其他业务事实，不自动重试未知结果。

## 4. 共享前端与两种执行方式

```text
UIX 源码 / 包内依赖
  → 共享 SourceGraph、CST、AST
  → 名称解析、类型与效果检查、能力登记
  → 共享类型化语义模型（界面 + 应用模块）
      ├─ Rust Emitter → Rust / Cargo → AOT 应用
      └─ 动态 lowering → 可验证执行计划 + UI 模板 → 动态模块实例
```

现有 `TypedUiIr` 仍表达 UI，不把业务指令强塞进它。应用模块需要对应的类型化表示；共享的是语言事实和分析阶段，不要求所有入口依赖一份巨型对象。动态执行计划可以从简单的有类型节点开始，是否使用字节码由测量决定；本计划不预设自研 JIT。

两条路径共用函数、数据、控制流和 UI 语义；不分别维护解析器、隐式转换、状态更新或错误规则。动态执行器由 app 拥有实例与资源，Compiler System 只负责分析和产物，不拥有窗口、领域状态或运行中的任务。运行期源码加载按需复用前端，按需打包解析部分，不把 Rust Emitter、LSP 与完整开发工具带进运行路径。

### 既有 Rust 绑定的兼容

当前根表达式允许从宏调用处解析 Rust 符号，部分类型和借用依赖 rustc 检查。这种语义无法原样用于只有文本的动态入口。

- 原有 AOT 宏保持现有行为，不要求旧应用迁移，也不在失败时自动转动态执行。
- 可动态加载模块的自由名称必须来自模块声明、参数、显式导入或已登记宿主端口；公开输入输出必须属于动态绑定支持的类型。
- 无法动态绑定的 Rust 类型 / 函数在装载前明确拒绝，并报告名称、来源与所需契约。不能从进程内任意查找符号，不能静默将类型转换成字符串。
- 同一可移植模块通过 AOT 和动态入口执行时，应有相同的可观察结果；仅 AOT 可用的绑定在工具中显式标注，不承诺所有历史 `.uix` 都能直接动态加载。

### 语义一致性门禁

补充方案进入实现前必须冻结数值宽度、溢出 / 除零、浮点特殊值、短路及参数求值顺序、字符串索引单位、集合复制 / 修改、错误和状态提交规则；这些要求不追加到已冻结的 Scheme P0。新模块不能依赖 Rust debug / release 的差异；其 AOT 生成按同一规则执行必要检查。已发布的旧 UI 表达式不借此静默改变行为，兼容变化须显式版本化。

用同一模块、同一输入和等价宿主端口分别经过真实 AOT 与动态执行，比较返回值、状态、效果顺序和失败；异步只比较合同规定的因果顺序，不强求无关任务的墙钟调度相同。语言等价不表示执行速度、诊断堆栈或资源耗尽阈值相同。

## 5. 动态界面与加载成本

`.uix` 仅在加载或源码依赖改变时解析与校验，形成可复用 UI 模板和已绑定的表达式。状态变化按依赖失效重新求值相应绑定，结构变化才协调子树；布局、绘制与命中不重新解析源码，也不执行应用业务动作。

布局需要的纯展示结果在对应 UI 提交前准备好，由既有 ui 运行时消费；不能让窗口 owner thread 同步等待后台业务脚本。已发布 AOT 控件局部交互语义保留，动态绑定怎样衔接同步事件消费见[宿主设计](../../架构/app/extensions.md#7-状态迁移与动态界面)。

解析开销、加载峰值、常驻状态和每次求值开销分别测量。缓存身份至少覆盖内容与依赖摘要、语言版本、能力集、宿主契约和执行计划版本；缓存有容量与释放策略。正常空闲不扫描模块、不固定轮询、不要求持续执行 UIX。

后续可以在打包时生成可加载产物，把解析工作提前到构建期。该产物需要自己的版本、验证与失效规则；不把当前编译器私有 IR 内存布局当稳定磁盘格式，也不在第一阶段强制发明二进制包或字节码规范。

## 6. 生命周期与内存

应用模块使用类型化 owned 值和受控状态句柄，不直接暴露 Rust 借用或私有实例。参数复制、只读共享、更新时复制等策略应有统一可观察语义；物理优化由实现选择。第一版优先限制可逃逸闭包和循环可变对象，避免仅为动态装载就预设复杂 GC。

实际启用的值图、回调、异步帧和资源句柄仍必须证明可回收；如果允许形成循环，则选择能回收循环的方案并验证。限制数据模型不能掩盖泄漏。存活字节、单次分配、执行步数、调用深度、队列与回收时间分别有预算；编译器和宿主原语同样受输入规模限制。

热替换仅迁移显式导出的类型化数据，不迁移指令位置、调用栈、闭包或挂起的执行帧。旧任务排空、取消或通过宿主明确支持的协议交接；新实例通过 schema 迁移恢复状态。候选实现应复用[扩展运行时](../../架构/app/extensions.md)中与语言无关的提交与失败责任；需要适配的部分在补充方案内另行定义，不反向要求主方案重构。

## 7. 工具与演进

check、fmt、query、LSP 和 AOT / 动态装载共同消费语言分析结果。新增模块、函数、类型和宿主端口要能定位定义、报告类型 / 效果错误、展示动态可用性；运行失败映射到原 `.uix` 来源与模块代。不能只让运行器认识语法而编辑器和 AOT 使用另一套规则。

当前规范与指南继续只说明实际已登记能力。新设计逐项落地、通过公开消费者后，再把具体规则迁入规范；目标样例不进入 `uix-compile` 等可复制围栏。当前不修改语言规范、公开 API 或发布承诺。

## 8. 与主方案的衔接及后续评估

Scheme 的 P0–P4 按[原实施计划](../../架构/动态扩展实施计划.md)继续；以下评估顺序独立于该计划，不是当前交付的前置条件：

1. **动态界面入口**：先评估把 `.uix` 解析为可复用界面模板，业务仍通过已登记的宿主或 Scheme 端口提供。验证名称绑定、属性求值、稳定 key、事件路由和失败后保留旧界面，单独衡量这一增量是否值得引入。
2. **UIX 应用模块**：再评估类型化函数、业务状态与异步流程，使 UIX 能直接实现新算法。以同一文本处理扩展对照 Scheme 方案，比较表达能力、重复代码、工具支持、加载时间、常驻内存、执行成本和语言维护量；不预设自研运行器更快或更轻。
3. **组合与兼容**：如果两条能力需要共存，分别声明语言、入口、兼容版本和所需构建能力；使用有版本的数据契约连接，不能隐式猜测语言、回退执行或自动翻译 `.scm`。状态由一个实例或宿主端口拥有，避免跨语言双写；闭包、解释器对象和执行帧不跨边界。

每一步先形成可审阅的语义、接入与验收方案，获得具体实施指令后再排期。是否共用包格式、是否抽出多引擎接口，以实际接入需求和兼容证据决定；当前不为预留该路线扩充 Scheme 引擎抽象或依赖。
