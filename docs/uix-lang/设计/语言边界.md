# UIX Lang 语言边界

[← 返回 UIX Lang 索引](../README.md)

> **文档角色**：长期设计——持有 UIX Lang 与 Rust Application System、UI Runtime System 之间的职责边界。
>
> **状态声明**：长期有效。本文定义非目标和所有权，不表示某项语法已经登记；当前语法与可用性分别以[规范](../规范/总览.md)和[参考](../README.md#文档地图)为准。

## 0. 两类语义的边界

自可移植应用模块获准后，原“UIX Lang 只描述 UI”不再覆盖全部语言。下文第 1–8 节明确限定为**旧 UI 描述层**（`uix!` / `uix_app!` / `uix_items!`），保留既有行为与不做事项，不以文件后缀排除新增 `<Module>`。

可移植应用模块独立遵守[应用模块规范](../规范/应用模块.md)：允许扩展自己的函数、类型化状态、命令和显式宿主异步端口；AOT 与动态消费共同前端和执行合同。Rust 宿主持有领域权威、授权、文件/网络/原生能力及进程生命周期，模块不能捕获任意 Rust 对象。Scheme 主方案继续独立，不要求迁移。候选设计与实际首版差距见[补充方案](应用模块与动态执行.md)和TASK-066（内部历史记录，不作为公开版本说明）。

## 0.1 组件创作与双路径目标

> **状态（2026-09-12）**：已明确产品方向，本轮只更新设计文档，尚未实现新的统一组件模型。下文不把目标语法或接口当作现有能力；当前两类入口仍按各自规范使用。

组件开发应接近前端的简便体验：以声明、组合和复用完成普通组件，不要求作者先实现控件内核，也不只是把 Rust 中的视觉参数搬到 `.uix`。框架负责衔接声明、状态更新、事件和运行实例；普通组件不应为了可用而重复手写 Rust 包装、属性登记和另一套动态描述。

### 组件组织

- **纯 `.uix`**：组件可以仅用 UIX 描述结构、样式、输入、局部状态、简单交互与子组件组合，不强制附带 `.rs`。
- **`.uix + .rs`**：需要复杂逻辑、异步任务、系统能力或自定义绘制时，可增加 Rust 实现。Rust 是按需扩展，不是每个组件的必备模板文件。
- 两种组织对调用方提供一致的组件接口与组合方式；内部是否带 Rust 不应改变属性、事件或插槽的使用模型。

这里的“纯 UIX”指组件作者不必编写配套 Rust 文件，不表示应用无需框架运行时或宿主。文件命名、关联方式、状态与方法的具体声明和自动绑定语法另行设计，本轮不冻结新语法。

### 一份定义，两种使用方式

| 路径 | 目标行为 |
| --- | --- |
| 静态编译 | 同一份组件定义参与构建，生成 Rust 并编译为原生代码；仅使用静态组件的应用不必携带动态加载能力。 |
| 动态加载 | 运行中的应用加载组件定义并创建实例，不要求为每次 UIX 组件变更重新编译宿主。 |

两条路径应共享语言含义和组件合同：相同输入下，属性、状态更新、事件、插槽、子组件组合与实例生命周期具有一致的可观察行为。作者不应为编译和动态加载分别维护两份组件；检查和错误位置也应对应原 UIX 来源。执行方式不同不要求性能或内部实现完全相同。

带 Rust 的组件同样面向这一双路径目标，但 Rust 能力需要可绑定的已编译实现；动态读取 `.uix` 不会直接执行 `.rs` 源码。Rust 绑定合同、是否支持独立编译的扩展产物，以及加载格式另行设计，不在本轮预选原生动态库、Wasm、解释器或 JIT 方案。

### 当前基础与待收敛部分

目前普通 `<Widget>` 主要经 UI 描述 AOT 路径展开；可移植 `<Module>` 已有共享检查、AOT 生成和运行期源码加载入口。两种机制并存，不等于所有现有 Widget 已能原样动态加载，也不等于统一组件开发体验已完成。现有 `<Visual>` 与 Rust 内核桥接可继续服务当前控件，但仅完成静态参数迁移不足以满足新的创作目标。

后续设计需要收敛两类入口的组件模型和绑定方式，再确定迁移范围与验收。具体语法、兼容取舍、热替换与状态保留策略留待讨论；本次文档更新不实施源码迁移，不改变既有 Scheme 扩展路线，也不将 UIX 扩展成通用编程语言作为前置条件。

## 1. 旧 UI 描述层承诺

UIX Lang 的旧 UI 描述层只负责界面，不承担应用模块的业务语言职责。使用方在 `.uix` 中声明界面结构、样式、展示数据、界面状态和局部交互；Rust 实现业务规则、领域模型、服务与应用流程。

```text
Rust Application System（业务真值、能力与流程）
        │ props / State<T> / 类型化回调
        ▼
UIX Lang（界面描述、界面状态与交互绑定）
        │ 编译期生成
        ▼
UI Runtime System（View、Widget、布局、绘制与事件）
```

旧 UI 描述层的正式构建只生成 Rust UI 代码，不引入 UIX Lang 解释器、虚拟机、字符串服务注册表或未类型化业务状态字典。

框架另有[标准 Lisp 软件动态扩展](../../架构/app/extensions.md)，用于扩展自己的业务逻辑、流程与动态界面，已有公开实现。它是独立按需启用的宿主能力，不改变旧 UI 描述的 AOT 和职责边界；本页“Rust 负责”描述宿主责任及 `.uix` 不得取得的能力，不禁止 Lisp 经授权端口实现扩展业务。Lisp 的状态归属、生命周期与 UI 投影以该目标设计为准。

## 2. SMC 所有权

| 边界 | 拥有 | 不取得 |
|---|---|---|
| Rust Application System | 业务契约、领域状态、服务、失败语义、跨 System 流程与应用生命周期 | UI Runtime 的私有 Widget 状态和编译器内部 IR |
| UIX Lang | UI 文档结构、界面输入投影、局部界面状态、展示派生和事件绑定 | 服务实例、事务、执行器、领域状态机和跨 System 生命周期 |
| UI Runtime System | View、Widget、State 句柄、布局、绘制、事件传播和界面状态生命周期 | 业务决策、持久化与应用流程 |

UIX Lang 描述的是 Application System 面向 UI 的 Adapter。它可以调用 Rust 显式提供的窄契约，但不取得这些契约背后的状态或实例所有权。

## 3. UIX Lang 负责

- 界面树、Widget 组合、Slot、If / For 渲染和静态应用外壳配置；
- 样式、主题、状态伪类、动画和可访问性描述；
- 文本插值、展示值派生、列表投影和只读格式化；
- 输入草稿、展开、选中、分页、弹层开关等短生命周期界面状态；
- UI 事件与 Rust 回调的绑定；
- 只影响当前界面的同步 action，例如组合多个局部状态更新、选择样式和提前结束当前处理器。

界面状态不能成为订单、权限、余额、任务进度等领域事实的唯一真值。业务结果需要反映到界面时，由 Rust 更新 `State<T>` 或 props，再由 UIX Lang 描述如何呈现。

## 4. Rust 负责

- 业务规则、领域模型、业务校验、授权与状态转换；
- 网络、数据库、文件、Settings、凭据和平台能力；
- 异步任务、取消、超时、重试、并发与错误恢复；
- 导航决策、多窗口编排、应用启动/关闭及资源生命周期；
- 业务事件、跨 System 协作和可持久化消息；
- 需要复杂算法、测试替身或独立契约的任何能力。

Rust 通过值 props、`State<T>` props、回调 props、`external` 或组合根向 UI 暴露窄契约。UIX Lang 可以触发这些契约，但不能根据请求已发送或传输已接管推断业务完成。

## 5. 状态与回调边界

| 需求 | 所有者 | UIX Lang 表达 |
|---|---|---|
| 当前输入草稿、展开或弹层开关 | 当前 Widget 实例 | 私有 `state` + `setState` |
| 多个界面组件共享的纯界面状态 | Rust 调用方 | `State<T>` prop；UIX 读取或显式更新同一句柄 |
| 领域真值或业务决策结果 | Rust Application System | 值 prop / `State<T>` prop，只展示结果 |
| 发起业务操作 | Rust 回调所有者 | 回调 prop 或 `external`，UIX 只绑定与传参 |
| 异步进度、失败和重试 | Rust Application System | Rust 管理生命周期并把显示状态投影给 UI |

`State<T>` prop 的可写性不转移所有权：句柄仍由 Rust 调用方拥有，UIX 的 `setState` 只通过该句柄提交一次同步界面更新。完整判定矩阵见[组件规范](../规范/组件.md#22-状态输入与可写绑定)。

## 6. 同步 action 的边界

已登记的无参数同步 action 和 `do { ... }` 只承担**界面交互编排**：

- 可以读取 props、界面 state 和 computed；
- 可以更新私有 state 或显式 `State<T>` prop；
- 可以切换主题/样式、调用同组件 action；
- 可以调用 Rust 提供的显式回调，把业务输入交给 Rust；
- 不登记参数化业务 Action、Service、`await`、重试、事务、路由或生命周期语法；
- 不把异步结果、业务错误或领域状态机放入 `.uix`。

当 `if` 判断涉及业务政策而不是呈现差异时，判断必须在 Rust 中完成，UIX Lang 只消费结果。

## 7. 判断规则

新增能力只有同时满足以下条件，才可以进入旧 UI 描述层；应用模块按第 0 节的专属规范评估：

1. 结果只描述或连接 UI，不建立新的业务真值；
2. 可以在编译期降低为确定的 Rust UI 语义；
3. 不需要 UIX Lang 拥有服务、执行器、事务或跨 System 生命周期；
4. 失败可以在编译期诊断，或由既有 UI Runtime 契约明确处理；
5. 不能满足时，可通过窄 Rust 回调或 prop 完成，而无需复制业务实现。

任一条件不满足，能力留在 Rust。

## 8. 明确非目标

- 把旧 UI 描述入口隐式改成应用脚本、工作流或通用编程语言；
- 在语言中声明 Service、事务、线程、执行器、原生句柄或持久化；
- 以 Function / Service 包装把业务逻辑迁入 `.uix`；
- 让局部界面 state 取代 Rust 领域状态；
- 让开发期动态能力成为生产正确性的依赖；
- 在 AOT 失败时自动回退为动态解释执行。
